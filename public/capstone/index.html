전체 구조

전체 구조는 이렇습니다. 자세히 보실 필요는 없고 두 가지만 보시면 됩니다. 왼쪽에서 들어오는 사용자 요청은 Cloudflare를 거쳐 클러스터로 들어오고, 앱은 아래쪽 각자의 공간(네임스페이스)에서 돕니다. 위쪽 GitHub의 Actions도 보시면, 앱 저장소에 push하면 Actions가 kodeploy CLI로 Core에 재배포를 요청합니다. GitHub가 주는 1회용 OIDC 토큰으로 인증해서, 저장해 둘 비밀키가 없습니다. 파란 선은 웹 터미널입니다. 브라우저는 1회용 티켓으로 Envoy를 거쳐 앱마다 둔 exec 게이트웨이에 붙고, Core는 서명한 요청으로만 게이트웨이에 부탁합니다. Core 자신은 앱에 직접 접속할 권한이 없습니다. 가운데 Core → Builder → GitHub → Argo CD로 도는 고리가 배포입니다. 이걸 다음 장에서 풀어 보겠습니다.

버튼을 누르면

배포 버튼을 누르면 다섯 단계가 돕니다. 1 요청: 웹에서 배포 버튼을 누르거나, git push하면 GitHub Actions가 CLI로 요청합니다. Core API가 요청을 받고 앱이 살 공간을 만들고, 빌더에게 빌드를 맡깁니다. → 2 빌드: 빌더가 클러스터 안에 BuildKit 작업을 띄워 git clone. Dockerfile이 없으면 nixpacks가 자동으로 만듭니다. 로그는 1초마다 화면으로. → 3 저장: 만든 이미지를 GitHub 레지스트리(GHCR)에 올립니다. → 4 기록: 빌더는 서버를 직접 건드리지 않고, Git의 앱 설정 파일(values.yaml)에 새 이미지 주소만 커밋합니다. → 5 배포: Argo CD가 그 Git을 읽고 서버를 그 상태로 맞춥니다. 앱이 제대로 뜨는지까지 확인하고, 주소는 바로 열립니다. 정리하면, 빌더는 서버를 직접 건드리지 않고 Git에 기록만 하고, 실제 서버는 Argo CD가 그 기록대로 맞춥니다. 그래서 롤백은 이전 커밋으로 되돌리는 것입니다.

이 서비스는 남의 코드를 제 서버에서 돌려 주는 서비스입니다. 그래서 한 앱이 다른 앱이나 플랫폼을 건드리면 안 됩니다. 앱마다 공간(네임스페이스)을 따로 주고, 양파처럼 겹겹이 막았습니다. → 권한: 앱은 root가 아닌 사용자로만 돌고, 권한 상승이 막혀 있고, 클러스터 토큰도 없습니다. 관리자 권한을 가져갈 수 없습니다. → 자원: CPU, 메모리, 디스크에 상한이 있어서 한 앱이 서버를 독차지 못합니다. → 네트워크: 다른 앱, 플랫폼, 내부망으로는 못 가고 바깥 인터넷만 나갑니다. 빌드도 같은 규칙입니다. → 커널: 컨테이너는 서버 커널을 같이 쓰기 때문에, gVisor 샌드박스로 한 겹 더 막아서 컨테이너를 탈출해도 서버에 닿지 않게 했습니다. (질문 대비) 플랫폼 자신의 권한도 줄였습니다. 클러스터 전역 권한 35개 → 6개, 앱에 직접 접속(exec)하는 권한 0개. 사용자는 kubectl 없이 웹으로만 요청합니다.

(질문 대비) 로그도 사용자 입력이라 AI를 속이려는 문장이 들어올 수 있어서, AI에는 아무 도구도 주지 않고 결과는 그 사용자 화면에 보여 주기만 합니다.
