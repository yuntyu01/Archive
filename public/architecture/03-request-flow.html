KoDeploy 아키텍처 · 03 / 07

요청 흐름

앱 방문자 · 플랫폼 사용자 · 운영자, 세 종류의 요청이 들어오는 길

읽는 법

  • 앱 방문자 - {앱}.kodeploy.com · {앱}-api.kodeploy.com은 와일드카드 DNS로 이미 NLB를 가리켜서, 새 앱도 DNS 작업 없이 바로 열린다. 커스텀 도메인은 Cloudflare for SaaS의 custom hostname으로 같은 길에 합류한다.
  • origin 검증 - Cloudflare Transform Rule이 비밀 헤더를 붙이고, 모든 HTTPRoute가 그 헤더 값을 매칭 조건으로 가진다. NLB 주소를 알아내 Cloudflare를 우회해도 맞는 라우트가 없다.
  • 슬롯 두 개 - 앱 하나에 서버 슬롯과 정적 슬롯이 있고, 각각 Service · HTTPRoute를 따로 가진다. 정적 슬롯을 켜면 {앱} 주소가 정적으로 넘어가고 서버는 {앱}-api에 남는다.
  • 플랫폼 사용자 - 웹 콘솔은 Workers 정적 웹이고, API 요청만 클러스터로 들어온다. Core는 세션과 앱 소유권을 확인한 뒤에만 K8s API · Builder를 부른다. 사용자에게 kubectl은 없다.
  • 웹 터미널(앱 셸 · DB · Redis 콘솔) - Core는 앱 주인에게 30초짜리 1회용 티켓만 주고, 브라우저는 그 티켓으로 api.kodeploy.com/exec/<ns>에 붙는다. Envoy가 그 테넌트의 kodeploy-exec로 보내고, 게이트웨이가 자기 ns Pod에만 exec한다. 티켓은 URL이 아니라 WebSocket 서브프로토콜로 넘기고, 이 라우트는 Cookie 헤더를 지워서 플랫폼 세션이 게이트웨이에 닿지 않는다. SQL 실행 · 테이블 탐색 · 덤프 · 복원은 Core가 HMAC 서명 요청으로 같은 게이트웨이의 내부 문(core Pod에서만 열림)에 부탁한다.
  • 운영자 - master 노드 호스트의 cloudflared가 밖으로만 연결을 맺는다. 관리자는 이 터널로 master에 SSH로 들어가 kubectl을 쓰고, 워커는 master를 거쳐(ProxyJump) 들어간다. Grafana는 외부에 열지 않고 port-forward로만 본다.
