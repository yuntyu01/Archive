설계 포인트

  • RBAC으로 못 하는 건 admission으로 - RBAC은 "이 이름 패턴의 ns만"을 표현하지 못해서, ns 생성과 RoleBinding 생성은 전역으로 줄 수밖에 없다. 그 요청의 모양을 ValidatingAdmissionPolicy(CEL)가 검사한다. Core가 털려도 argocd 같은 이름으로 ns를 만들거나 거기에 자기 권한을 걸 수 없다.
  • ns 삭제도 RoleBinding으로 - ns 안 RoleBinding이 주는 namespaces 권한은 그 ns 객체 하나에만 닿는다. 그래서 삭제를 전역에서 빼고 테넌트 롤에 넣어, Core가 지울 수 있는 ns를 RBAC만으로 "자기 RoleBinding이 걸린 테넌트 ns"로 좁혔다. ns 읽기도 없앴다 - 지운 직후 재배포할 때의 Terminating 대기는, RoleBinding 생성이 NamespaceTerminating 사유로 거절되는지로 판정한다.
  • 읽기는 RBAC으로만 - Secret 읽기는 admission을 거치지 않는다. 그래서 이 권한은 ClusterRole로 정의만 하고, 테넌트 ns마다 RoleBinding으로 건다. Core는 ns를 만들 때 자기 RoleBinding부터 걸고, 권한이 반영될 때까지 SelfSubjectAccessReview로 기다린 뒤 Secret을 쓴다.
  • exec는 권한을 좁히는 대신 떼어 냈다 - Pod exec는 RoleBinding으로 ns를 좁혀도 "그 ns의 아무 Pod에 아무 명령"이다. 그래서 Core에서 빼고, 테넌트 ns마다 뜨는 kodeploy-exec(Go)가 자기 ns Pod에 정해진 작업만 한다. Core는 HMAC 서명 요청과 1회용 티켓 발급만 하고, 터미널 바이트는 Core를 거치지 않는다. 게이트웨이 SA에는 Secret 권한이 없어서 DB 비밀번호는 DB 컨테이너의 env에서 읽고, pods/exec를 가진 SA라 VAP가 그 SA로 뜰 수 있는 Pod를 이미지 digest까지 묶는다.
  • kubelet은 통계만 - 관리자 노드 현황은 nodes/proxy 대신 kubelet /stats/summary를 직접 부르고 nodes/stats만 쓴다. kubelet 서빙 인증서는 노드마다 자체 CA라, 그 CA들을 ConfigMap으로 모아 TLS를 검증한다.
  • 검증 - 적용할 때마다 Core SA로 위장한 kubectl auth can-i와 server dry-run으로 허용 · 거부를 하나씩 확인했고, 적용 뒤 403은 0건이었다. 테넌트 ns로 한정할 때는 임시 ns를 Core 함수로 만들고 지워 실제 경로를 확인했고, ns 권한 축소는 운영과 같은 버전(K8s 1.35)의 로컬 클러스터에서 Core 함수로 삭제 직후 재배포까지 돌려 확인했다. exec 회수는 can-i 대신 실제 exec 요청으로 확인했다(회수 전 허용 → 회수 뒤 403). exec 연결은 GET으로 열리지만 create로 인가돼서, 묻는 동작에 따라 can-i 답과 실제 판정이 어긋난다 - get만 남겨 봤을 때 can-i는 허용, 실제 연결은 403이었다.
