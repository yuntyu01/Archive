KoDeploy 아키텍처 · 02 / 07

배포 흐름

웹 · CLI · GitHub Actions에서 시작한 배포를 Core가 커밋 SHA와 함께 Builder에 맡기고, Builder가 그 커밋으로 이미지를 만들어 값 저장소에 커밋하면 Argo CD가 배포한다

저장소 넷, 쓰는 주체도 하나씩

저장소담는 것쓰는 주체
kodeployCore API · Builder 코드, 플랫폼 매니페스트, Terraform · Ansible사람
kodeploy-charts앱 하나를 그리는 Helm 차트, ApplicationSet · AppProject사람만 push
kodeploy-apps앱별 apps/<ns>/values.yaml (이미지 digest · 환경 · 도메인)Builder만 커밋
deploy-actionGitHub Actions에서 CLI를 받아 재배포하는 composite 액션, CLI 체크섬 (공개)사람

설계 포인트

  • Core는 워크로드를 만들지 않는다 - Deployment · Service · HTTPRoute · NetworkPolicy · DB는 차트가 그리고 Argo CD가 apply한다. Core는 그 앞의 준비(②)와 조회 · 로그만 맡는다. 터미널 · DB 작업은 테넌트마다 뜨는 kodeploy-exec가 한다.
  • 시작점은 셋, API는 둘 - 웹의 "설정 변경"은 배포 폼(POST /deploy)으로 설정을 정하고, 웹의 "배포하기" · CLI · GitHub Actions는 재배포 API(POST /apps/{id}/deploy/redeploy)로 지금 떠 있는 설정을 그대로 다시 쓴다. 자세한 것은 07 CI/CD.
  • 커밋 고정 - 재배포는 커밋 SHA를 requested_sha로 적고 Builder에 브랜치 대신 그 커밋을 ref로 보낸다. Builder는 그 커밋 하나만 fetch하고, clone 직후 init 로그에 찍은 KODEPLOY_SOURCE_SHA 한 줄로 실제 빌드한 커밋(source_sha)을 보고한다. main 컨테이너 로그는 사용자 Dockerfile이 찍을 수 있어 보지 않고, 요청과 다르면 배포 전에 실패시킨다.
  • 서명된 요청 - Core → Builder 요청과 Builder → Core 이벤트 모두 HMAC-SHA256(시각 · 메서드 · 경로 · 본문)으로 검증한다. 이벤트는 2xx를 받을 때까지 다시 보낸다.
  • push 완료가 빌드 완료 - 로그에서 이미지 push 완료 마커를 찾으면(⑥) 다음 빌드용 cache export를 기다리지 않고 바로 배포 단계로 넘어간다.
  • 성공 판정은 두 겹 - Argo가 이 커밋으로 Synced + Healthy인지(⑫)와 앱 Pod가 반복해서 죽지 않는지(⑬)를 함께 본다. 롤아웃이 끝난 뒤 크래시하는 앱을 Argo는 바로 Degraded로 보지 않기 때문이다.
  • 같은 길로 바뀐다 - 환경변수 변경 · 롤백 · 삭제도 Core → Builder → values.yaml 커밋 → Argo sync 경로를 그대로 탄다. 실패하면 Core가 로그를 LLM 게이트웨이에 보내 원인 요약을 붙인다.
