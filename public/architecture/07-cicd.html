CLI exit code

exit뜻액션의 잡 결과
0성공. 모두 running이 되고 settle(기본 60초) 동안 그대로성공
1배포 실패. 빌드 하나라도 failed실패
2사용법 오류, 다시 보내도 같은 400, 409, 422실패
3다른 배포에 밀림. 실패 없이 cancelled기본은 notice만 남기고 성공(fail-on-superseded: true면 실패)
4CLI 시간 제한(기본 25분) 초과. 빌드는 서버에서 계속 진행실패
125인증, 권한, 연결 오류실패
130사용자가 중단(SIGINT, SIGTERM)실패

상태 조회는 2초에서 시작해 바뀌지 않으면 두 배씩 10초까지 늘리고, 어느 빌드든 바뀌면 2초로 돌아간다. --output json은 결과 하나를 stdout에 쓰고, GITHUB_ACTIONS=true면 실패할 때 ::error 한 줄과 잡 요약 표를 남긴다.

스크립트는 셋이다. install.sh는 id-token 권한, 러너 OS와 아키텍처를 확인하고 CLI를 받아 고정 체크섬과 비교한다. deploy.sh는 CLI를 돌리고 출력을 채운다. lib.sh는 둘이 같이 쓰는 함수다. 입력은 env로만 넘긴다.

설계 포인트

  • 설정은 웹 폼만 바꾼다 - 재배포 API는 설정을 요청으로 받지 않고 슬롯마다 지금 떠 있는 배포 행에서 다시 만든다. CI는 커밋만 바꿀 수 있다.
  • 입력과 출력의 지문 - 요청 시점에는 이미지가 없어서 커밋 SHA로 고정하고, 결과는 이미지 digest로 Argo CD에 넘긴다. 워크플로는 액션을 커밋 SHA로, 액션은 CLI 바이트를 커밋해 둔 sha256으로 고정한다.
  • 겹치는 배포 - 서버는 같은 슬롯의 진행 중 빌드를 취소하고 마지막 요청을 살린다. 밀린 쪽 CLI는 exit 3이고 액션은 notice만 남긴다. 2026-11-23 실측(세 안 2회씩)에서 deploy 잡을 차례로 세우던 concurrency를 빼자 두 번째 push가 운영에 나가기까지가 평균 466초에서 257초로 줄어, 데모 워크플로에서 뺐다.
  • 짧은 토큰과 재교환 - CI 토큰은 15분이고, 서버 쪽 최대 대기는 약 23분이다. CLI가 대기 중 401을 받으면 새 ID 토큰으로 다시 교환한다(실행당 최대 5번). 운영 기록의 배포 43회에서 가장 긴 대기는 8분 11초였다.
  • 안정화 - 서버는 서버 빌드가 running이 된 뒤 60초 동안 앱 Pod를 더 보고 재시작 · OOM이면 같은 빌드를 failed로 바꾼다. 그래서 CLI도 모두 running이 된 뒤 60초를 더 기다린 다음 성공으로 끝낸다.
  • 확인 - 2026-11-21~23 시험 앱(서버 저장소 A, 정적 저장소 B)에서 push 성공, 테스트 실패 시 배포 건너뜀, 연속 push 대기, Re-run 새 빌드, 웹 배포와 겹친 밀림, 액션 SHA 고정을 GitHub Actions 실행으로 확인했다. B에 배포하지 않은 커밋을 올려 두고 A에 push해도 정적 슬롯은 라이브 커밋으로 빌드됐다.
