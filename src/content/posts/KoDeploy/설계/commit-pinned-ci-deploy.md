> **요약**
>
> - 빌더가 브랜치 최신을 받아서, CI가 테스트한 커밋과 배포된 커밋이 다를 수 있었습니다. 11월 23일 데모 저장소에서 다시 재현했습니다.
> - 요청에 커밋 SHA를 싣고 빌더가 그 커밋만 받아 보고하게 했고, CI 인증은 저장 토큰 대신 GitHub OIDC 교환(검사 9개, CI 토큰 15분)으로 했습니다.
> - 운영 기록의 배포 43회로 기다림의 숫자를 검증했습니다. 토큰 15분, 시간 제한 25분, settle 60초는 기록과 맞았고, 조회 간격을 2초에서 10초로 늘리는 방식은 10초 고정보다 나은 점이 없었습니다.
> - 겹치는 배포는 concurrency 세 안을 2회씩 재서, 차례로 세우던 설정을 줄 없음으로 바꿨습니다. 두 번째 커밋이 운영에 나가기까지가 평균 466초에서 257초로 줄었습니다.
> - 교환은 아직 워크플로 파일(`job_workflow_ref`)을 보지 않아서, 같은 저장소의 다른 워크플로도 그 커밋을 배포할 수 있습니다.

## 들어가는 글

[지난 글](/blog/tenant-exec-gateway/)에서 core의 Pod exec 권한을 게이트웨이로 옮겼고, 이 글은 배포를 시작하는 쪽입니다.

11월 18일 전까지 KoDeploy에서 배포하는 방법은 웹의 배포 폼 하나였습니다. 코드만 바꿔 다시 배포할 때도 저장소, 브랜치, 런타임, 포트, DB를 처음부터 채워야 했습니다. 빌더는 `git clone -b <브랜치>`를 했고, 어느 커밋을 빌드했는지 남기는 칸도 없었습니다.

목표는 두 가지였습니다. 하나는 GitHub에 push하면 그 push로 돈 워크플로의 커밋이 그대로 배포되는 것입니다. 서버가 보장하는 것은 여기까지이고, 그 커밋이 테스트를 통과했는지는 사용자 워크플로의 `needs: test`가 지킵니다. 다른 하나는 그러기 위해 저장소에 오래 사는 비밀을 두지 않는 것입니다.

결정은 11월 18일부터 21일 사이에 했고, 그 결정이 맞는지는 11월 23일에 따로 쟀습니다. 실측마다 볼 지표와 결정 규칙을 먼저 글 초안에 적어 두었고, 결과를 본 뒤에는 바꾸지 않았습니다.

## 결정 1. 커밋으로 빌드하기

| 안 | 빌드하는 커밋 | 실제로 빌드한 커밋 |
| --- | --- | --- |
| 그대로 (`clone -b <브랜치>`) | 빌더가 clone하는 순간의 브랜치 최신 | 모름 |
| core가 GitHub에 브랜치의 SHA를 물어 그 값으로 | 물어본 순간의 최신 | core가 물어본 값으로 짐작 |
| 요청에 SHA를 싣고 빌더가 그 커밋만 받음 | 요청한 커밋 | 빌더가 받은 HEAD를 보고 |

기준은 요청한 커밋과 실제로 빌드한 커밋이 같다는 것을 서버가 확인하고 남길 수 있는가였습니다. 둘째 안은 묻고 받는 사이에도 브랜치가 움직이고, 실제로 받은 커밋은 여전히 빌더만 압니다.

결정 뒤인 11월 23일에 문제를 다시 재현했습니다. 데모 저장소에 커밋 A를 push하고, A의 test 잡이 도는 동안 커밋 B를 `[skip ci]`로 push했습니다. 판정은 앱이 내려주는 파일 본문(`repro-A`, `repro-B`)으로 했습니다.

| 배포 | 요청한 커밋 | 빌더가 받은 커밋 | 앱 응답 본문 |
| --- | --- | --- | --- |
| CI (A의 실행) | A `20a3ced` | A `20a3ced` | `repro-A` |
| 웹 "배포하기" (커밋 지정 없음) | 없음 (브랜치 최신) | B `87d5f60` | `repro-B` |

B는 A push 21초 뒤에 올렸고, CI의 서버 빌드가 소스를 받기 51초 전이었습니다. 커밋을 고정하기 전의 빌더였다면 이 빌드는 테스트를 거치지 않은 B를 받았을 것입니다.

이런 일이 생길 수 있는 구간, 곧 push부터 빌더가 소스를 받기까지를 최근 CI 실행 17회에서 쟀습니다. push 시각은 GitHub 실행이 만들어진 시각, 받은 시각은 빌드 Pod의 clone 컨테이너가 시작한 시각입니다(Pod가 지워진 4회는 빌드 생성 뒤 3초로 잡음). 중앙값 72초, 최대 285초였고, 최대는 앞 배포를 줄 서서 기다린 실행이었습니다.

11월 18일에 셋째 안으로 정했습니다. 빌더는 받은 `REF`가 40자 hex면 빈 저장소에 그 커밋 하나만 fetch하고, 받은 HEAD를 init 컨테이너 로그에 `KODEPLOY_SOURCE_SHA=` 한 줄로 찍어 core에 보고합니다. core는 `requested_sha`와 `source_sha`를 같이 남깁니다. 이 줄은 init 컨테이너 로그에서 처음 맞은 한 줄만 인정합니다. 뒤의 BuildKit 로그에는 사용자 Dockerfile의 `RUN`이 아무 글자나 찍을 수 있기 때문입니다. 두 커밋이 다르면 배포 전에 `failed`로 끝냅니다.

이 위에 재배포 API를 만들었습니다. 설정은 요청으로 받지 않고 슬롯(서버, 정적)마다 지금 떠 있는 배포 행에서 다시 만들어서, CI는 커밋만 바꿀 수 있습니다. 같은 슬롯의 진행 중 빌드는 취소되고 마지막 요청이 이깁니다. 네트워크 재시도를 새 배포와 구분하려고 `Idempotency-Key`를 받습니다. 요청과 응답 형식은 [아키텍처 07](/architecture/07-cicd.html)에 옮겨 두었습니다.

11월 21일 운영에 올린 뒤 리뷰에서 구멍 하나를 찾았습니다. CI 경로는 토큰과 저장소, 브랜치가 같은 슬롯만 토큰의 커밋으로 고정하고, 나머지 슬롯은 그 브랜치 최신으로 같이 다시 빌드했습니다. 시험 앱은 서버가 저장소 A, 정적 사이트가 저장소 B라서, B에 아직 배포하지 않은 커밋이 A의 테스트만 거쳐 나갈 수 있었습니다. [PR #13](https://github.com/kodeploy/kodeploy/pull/13)에서 나머지 슬롯을 지금 떠 있는 커밋으로 고정하고, 기록이 없으면 `409 slot_commit_unknown`으로 멈추게 했습니다.

## 결정 2. 인증

| | 저장 토큰 | OIDC 교환 |
| --- | --- | --- |
| 저장소에 두는 것 | 오래 사는 토큰 | 없음 (앱 id는 variable) |
| 새어 나가면 | 회수할 때까지 쓸 수 있음 | ID 토큰은 한 번만 교환, CI 토큰은 15분 |
| 할 수 있는 일 | 토큰 주인의 권한 | 그 앱, 그 커밋의 재배포와 상태 조회 |
| 교체 | 사람이 직접 | 실행마다 새로 받음 |
| 배포할 수 있는 사람 | 토큰을 아는 사람 | 배포 브랜치에 push하거나 그 브랜치로 workflow_dispatch를 돌릴 수 있는 사람(저장소 쓰기 권한) |

기준은 저장소에 오래 사는 비밀이 없을 것, 새어 나가도 쓸 수 있는 범위가 그 앱과 그 커밋으로 좁을 것이었습니다. 이 결정은 위 비교로 했고, 따로 재지는 않았습니다. 잡에 `id-token: write` 권한이 있으면 GitHub가 서명한 ID 토큰(JWT)을 받을 수 있고, 여기에 저장소, ref, 커밋 SHA, 이벤트가 들어 있습니다. core는 이 토큰을 검사해 15분짜리 CI 토큰을 줍니다.

![GitHub Actions에서 배포까지](/images/posts/commit-pinned-ci-deploy/01.png)

교환 API는 인증 없이 열려 있고 본문의 ID 토큰이 인증입니다. 그래서 서명을 확인하기 전에는 DB를 건드리지 않고, 아래 순서로 하나라도 걸리면 거절합니다.

| # | 검사 | 실패 |
| --- | --- | --- |
| 1 | 서명: GitHub JWKS의 키, `RS256`만 | 401 |
| 2 | `iss`가 `https://token.actions.githubusercontent.com` | 401 |
| 3 | `aud`가 `kodeploy` | 401 |
| 4 | `exp`, `iat`, `nbf` (시계 차이 60초 허용) | 401 |
| 5 | `jti` 1회용 (CI 토큰 표의 UNIQUE) | 401 |
| 6 | 앱이 있고 "GitHub Actions 배포 허용"이 켜져 있음 | 404, 403 |
| 7 | 이벤트가 `push` 또는 `workflow_dispatch` | 403 |
| 8 | 라이브 슬롯 중 저장소와 브랜치가 모두 토큰과 같은 슬롯이 있음 | 403 |
| 9 | `sha`가 40자 hex | 401 |

CI 토큰은 재배포와 상태 조회 두 라우트에서만 받고, 서버에는 sha256만 남습니다. "GitHub Actions 배포 허용"은 앱마다 기본으로 꺼져 있고, 끄면 발급된 CI 토큰도 그 자리에서 만료됩니다. 11월 21일부터 23일까지의 실행 로그에서 토큰 원문은 0건이었습니다.

## 결정 3. 기다림의 숫자

CLI가 빌드를 기다리는 데에는 숫자 네 개가 들어갑니다.

| 숫자 | 후보 | 11월 21일에 고른 값 |
| --- | --- | --- |
| CI 토큰 수명 | 10, 15, 20분, 서버 상한보다 길게 | 15분. 서버 상한 약 23분(빌드 Job 15분 30초 + Argo CD 대기 8분)을 한 장으로 버티면 새어 나갔을 때도 그만큼 쓸 수 있어서, 대기 중 `401`이면 다시 교환(최대 5번) |
| CLI 시간 제한 | 서버 상한보다 짧게, 길게 | 25분. 서버 상한보다 길게 |
| settle | 0초, 60초 | 60초. 서버는 서버 빌드가 `running`이 된 뒤 60초 동안 앱 Pod를 더 보고 재시작이나 OOM이면 `failed`로 바꿈(postwatch) |
| 상태 조회 간격 | 2초 고정, 10초 고정, 2초에서 두 배씩 10초까지 | 늘리는 방식. 바뀔 때는 빨리 알고 오래 기다릴 때는 요청을 줄이려고 |

11월 23일에는 이 값들을 운영 기록과 맞춰 봤습니다. 범위는 Argo CD로 옮긴 뒤 첫 빌드(10월 30일)부터 11월 22일까지의 빌드 66개, 배포 45회이고, 플랫폼 DB는 읽기 전용 세션으로만 조회했습니다. 미리 적은 규칙은 이렇습니다. 토큰 15분은 대기(모두 `running`까지 + settle 60초)가 15분을 넘는 배포가 5% 이하, 시간 제한 25분은 최대 대기와 서버 상한이 모두 25분 미만, settle은 서버 postwatch 창과 같으면 맞습니다. 조회 간격은 지금 방식의 요청 수가 2초 고정의 절반 이하이고 평균 감지 지연이 10초 고정보다 짧아야 맞고, 기록된 상태 변화 시각을 재생해 비교했습니다.

| 지표 | 값 |
| --- | --- |
| 요청부터 `running`까지 (중앙값, p95, p99, 최대) | 빌드 63개 80, 230, 431, 431초. 서버 슬롯 43개 119, 337, 431, 431초. 정적 슬롯 20개 76, 86, 92, 92초 |
| `running` 뒤 postwatch에서 `failed` | 서버 빌드 43개 중 1개 (2.3%) |
| 배포 한 번의 대기, 43회 | 중앙값 179초, p95 397초, 최대 491초 |
| 다시 교환이 필요한 배포 (토큰 10, 15, 20분) | 0%, 0%, 0% |
| 2초 고정 / 10초 고정 / 지금 방식 | 배포당 조회 142.5 / 30.2 / 39.3회, 평균 감지 지연 0.5 / 4.3 / 4.6초 |

![운영 기록으로 본 대기 시간과 폴링](/images/posts/commit-pinned-ci-deploy/04.png)

토큰 15분, 시간 제한 25분, settle 60초는 기록과 맞았습니다. 가장 오래 기다린 배포도 8분 11초였습니다. settle이 실제로 실패를 잡은 경우도 한 번 있었습니다. 11월 19일 시험 앱의 서버 빌드가 `running`이 된 뒤 시작 코드에서 죽어 `failed`로 바뀌었는데, settle이 0초였다면 CLI는 이 배포를 성공으로 끝냈을 것입니다. postwatch는 실패로 바꿔도 `deploy_ready_at`을 남기고 오류를 정해진 문구로 시작해서, 이 두 칸으로 셌습니다.

조회 간격은 규칙에 맞지 않았습니다. 요청 수는 2초 고정의 28%였지만, 평균 감지 지연은 10초 고정과 거의 같았습니다. `deploying`에서 `running`까지 중앙값 57초(가장 짧아도 13초)가 걸리는데, 간격은 바뀐 뒤 14초면 이미 10초가 되기 때문입니다. 바꾸지는 않았고 제안으로 남깁니다. 10초 고정이면 지연은 같고 요청이 23% 줄고, 5초 고정이면 배포당 58.3회에 평균 지연 1.9초입니다. 토큰을 10분으로 줄여도 기록상 다시 교환은 없지만, 서버 상한까지 기다리면 교환이 두 번 필요해서 그대로 두었습니다.

CI 경로에서 토큰 밖 슬롯을 라이브 커밋으로 다시 빌드한 5건은 73~80초로, 같은 실행의 서버 빌드(74~80초)와 나란히 돌아 배포를 늦추지 않았지만 빌더의 동시 빌드 세 자리 중 하나를 씁니다.

## 결정 4. 겹치는 배포

같은 브랜치에 push가 잇달아 오면 deploy 잡이 겹칩니다. 서버는 같은 슬롯의 진행 중 빌드를 취소하고, 그 빌드를 기다리던 CLI는 exit 3(밀림)으로 끝납니다. GitHub 쪽은 워크플로의 `concurrency`로 정합니다.

| 안 | 설정 | 예상 |
| --- | --- | --- |
| (a) | `group: deploy-${{ github.ref }}`, `cancel-in-progress: false` | deploy 잡이 차례로 돈다. 앞 커밋도 끝까지 배포된다 |
| (b) | 같은 그룹, `cancel-in-progress: true` | 새 deploy 잡이 앞 잡을 취소하고, 앞 서버 빌드는 새 요청이 취소한다 |
| (c) | `concurrency` 없음 | 두 잡이 같이 돌고, 서버에서 앞 빌드가 밀린다 |

11월 21일에는 (a)로 두었습니다. 돌고 있는 배포를 끊지 않고 다음 배포를 기다리게 하는 설정이고, 그날 연속 두 번 push했을 때 둘 다 성공했습니다. 다만 이 설정이 두 번째 커밋을 얼마나 늦추는지는 재지 않았습니다.

11월 23일에 세 안을 2회씩 쟀습니다. 커밋 A를 push하고 약 40초 뒤 커밋 B를 push했고, 커밋마다 앱이 내려주는 파일 본문을 바꿔 2초마다 읽어 A가 운영에 나갔는지를 판정했습니다. 미리 적은 규칙은 "B push부터 B가 `running`이 될 때까지가 (a)보다 30% 이상 짧고, 빌드 실패나 OOM이 없고, 빨간 잡이 없는 안이 있으면 그 안으로 바꾼다. 둘 다 해당하면 더 짧은 안, 없으면 (a) 유지"였습니다.

| 안 | B push부터 B `running`까지 | 취소된 빌드 (돈 시간) | 잡 결과 | A가 운영에 | 동시 빌드 Pod 최대 |
| --- | --- | --- | --- | --- | --- |
| (a) | 458.5초, 473.2초 | 0, 0 | 모두 초록 | 나감 (4분 5초, 4분 26초) | 2, 2 |
| (b) | 278.0초, 264.4초 | 1 (72초), 1 (67초) | A의 deploy 잡 회색(취소) | 안 나감 | 3, 3 |
| (c) | 267.0초, 247.2초 | 2 (108초), 2 (51초) | 모두 초록 (A 잡에 밀림 notice) | 안 나감 | 3, 4 |

![concurrency 세 안](/images/posts/commit-pinned-ci-deploy/05.png)

(a) 평균 465.8초의 70%는 326초입니다. (b)와 (c)는 둘 다 이보다 짧았고(평균 271.2초, 257.1초) 실패나 OOM, 빨간 잡도 없었습니다. 둘 다 해당하면 더 짧은 안을 고르기로 적어 두었으므로 (c)로 바꾸고, 데모 워크플로의 deploy 잡에서 `concurrency`를 뺐습니다. 둘의 차이 14초는 회차 사이 차이와 비슷한 크기라, 규칙이 아니었다면 가르기 어려운 차이였습니다.

(a)에서는 A가 매번 4분 넘게 운영에 나가 있었습니다. (b)는 A의 deploy 잡이 회색으로 남지만 실행 화면에 failure 등급 주석("The operation was canceled.")이 붙었습니다. (c)는 A의 잡이 자기 빌드가 취소된 것을 보고 exit 3으로 끝나 notice만 남기고 초록이었고, 대신 A의 정적 빌드까지 취소돼 취소가 2개였습니다. 동시 빌드 Pod가 빌더 상한(3)보다 많은 4개였던 회차는, 취소된 빌드의 Pod가 취소 뒤에도 26~31초 더 돌다 끝났기 때문입니다. 빌더는 취소하면 자리를 바로 돌려줘서 대기(429)는 없었습니다. (c) 2회차는 터널이 끊겨 Pod 감시가 21분 비었지만, 빌드가 겹친 1분은 기록 안에 있습니다.

## CLI와 액션

재배포 요청, 상태 조회, 판정을 워크플로 YAML에 curl로 쓰면 길고 틀리기 쉬워서 Go CLI(`kodeploy deploy`)로 묶었습니다. 하나라도 `failed`면 exit 1, 실패 없이 `cancelled`가 있으면 exit 3, 모두 `running`이고 settle이 지나면 exit 0입니다. 1은 이 커밋이 배포되지 못했다는 뜻이고 3은 더 새 배포가 이어받았다는 뜻이라 나눴습니다. exit code 전체 표는 [아키텍처 07](/architecture/07-cicd.html)에 있습니다.

워크플로에서는 composite 액션 [kodeploy/deploy-action](https://github.com/kodeploy/deploy-action)으로 씁니다. 셸 스크립트 세 개(설치, 실행, 공통)로 되어 있습니다. 릴리스의 `checksums.txt`만 믿으면 릴리스를 바꿀 수 있는 사람이 바이너리와 체크섬을 함께 바꿀 수 있어서, 기본 버전의 sha256은 액션 저장소에 커밋해 두고 비교합니다. 입력값은 `run:`에 끼우지 않고 env로만 넘깁니다. 입력과 출력 목록은 07에 있고, 데모 저장소의 deploy 잡은 지금 이렇습니다.

```yaml
deploy:
  needs: test
  runs-on: ubuntu-latest
  permissions:
    id-token: write
    contents: read
  steps:
    - uses: kodeploy/deploy-action@678ee39b122c1242a5b12a22c1431a187205fd49 # v1.0.0
      with:
        app: ${{ vars.KODEPLOY_APP_ID }}
```

## 운영 반영과 결과

11월 18일에 빌더 커밋 고정과 재배포 API, 웹 "배포하기", 19일에 커밋 고르기, 21일에 CI 인증([PR #11](https://github.com/kodeploy/kodeploy/pull/11)), CLI([PR #12](https://github.com/kodeploy/kodeploy/pull/12)), 슬롯 고정([PR #13](https://github.com/kodeploy/kodeploy/pull/13)), deploy-action v1.0.0을 운영에 올렸습니다. core를 바꿀 때마다 적용 전에 이미지 digest와 플랫폼 DB 덤프를 남겼고, 되돌린 일은 없었습니다. "GitHub Actions 배포 허용"은 시험 앱 하나에만 켰습니다.

| 항목 | 전 (11/18 전) | 후 (11/23) |
| --- | --- | --- |
| 배포를 시작하는 곳 | 웹 배포 폼 | 웹 "배포하기"와 "설정 변경", CLI, GitHub Actions |
| 빌드하는 커밋 | 브랜치 최신, 기록 없음 | 요청한 커밋 SHA, 실제 빌드한 커밋 기록 |
| 다른 슬롯 (CI) | 해당 없음 | 지금 떠 있는 커밋으로 고정, 기록 없으면 `409` |
| 저장소에 두는 비밀 | 해당 없음 | 0개. ID 토큰은 1회용, CI 토큰은 15분 |
| 같은 브랜치에 잇단 push | 해당 없음 | 앞 배포는 서버에서 밀려 exit 3(notice), 마지막 요청만 배포 |

push부터 배포까지는 액션의 커밋 SHA, CLI의 sha256, 소스의 커밋 SHA, 이미지 digest로 이어집니다.

## 한계

- 교환은 ID 토큰의 `job_workflow_ref`를 보지 않습니다. 같은 저장소와 브랜치의 다른 워크플로나, `id-token: write`가 있는 다른 잡(그 잡의 서드파티 액션 포함)도 audience를 `kodeploy`로 받은 ID 토큰으로 그 커밋을 배포할 수 있습니다. 다음 일은 앱마다 허용할 워크플로 지정과 배포 브랜치 보호입니다.
- 저장소를 이름(`owner/repo`)으로 비교합니다. 지우고 같은 이름으로 다시 만든 저장소도 같은 앱으로 배포할 수 있어서, ID 토큰의 `repository_id`로 비교하는 것이 다음 일입니다.
- 서버는 마지막 요청을 살릴 뿐 커밋의 앞뒤를 보지 않습니다. 앞 커밋의 test 잡이 더 늦게 끝나면 앞 커밋이 마지막 요청이 되어 남습니다. `concurrency`를 써도 GitHub는 도착 순서로 줄을 세워서 같습니다.
- CI가 테스트한 이미지를 그대로 배포하지는 않습니다. 빌더가 같은 커밋으로 이미지를 새로 만듭니다. CI가 만든 이미지를 받으려면 CI에 레지스트리 쓰기 권한을 주고 사용자가 만든 이미지를 믿어야 해서, 빌드 환경을 플랫폼이 쥐는 쪽을 골랐습니다.
- 사람이 터미널에서 쓰는 로그인과 GitLab CI는 아직 없습니다.
- 실측은 시험 앱 하나에서 안마다 2회, 운영 기록은 배포 45회입니다. 표본이 적어 p99가 최대와 같습니다.

전체 흐름과 API 형식은 [아키텍처 07 - CI/CD](/architecture/07-cicd.html)에 정리했습니다.
