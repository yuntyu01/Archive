> **요약**
>
> - 배포는 웹 화면 하나였고, 빌더는 브랜치 최신을 받아서 CI가 테스트한 커밋과 배포되는 커밋이 다를 수 있었습니다.
> - push로 배포되는 길을 내면서, 그 길로 할 수 있는 일을 그 워크플로가 돈 커밋을 그 앱에 배포하는 것 하나로 좁혔습니다. 요청에 커밋 SHA를 싣고, CI 인증은 GitHub OIDC 교환으로 해서 15분짜리 토큰만 오갑니다.
> - 운영에 올린 뒤 CI가 다른 슬롯까지 브랜치 최신으로 빌드하는 구멍을 찾아, 그 슬롯을 지금 떠 있는 커밋으로 고정했습니다.
> - 겹치는 배포 설정은 세 안을 실측해 바꿨고, 두 번째 커밋이 운영에 나가기까지가 평균 466초에서 257초로 줄었습니다.

## 배경

[지난 글](/blog/tenant-exec-gateway/)에서 Pod exec 권한을 API 서버에서 테넌트별 게이트웨이로 옮겼고, 이 글은 배포를 시작하는 쪽입니다.

KoDeploy에서 배포를 시작하는 곳은 웹 화면 하나였습니다. 저장소를 고르고 버튼을 누르면 빌드해서 배포합니다. 클릭만으로 배포하는 것이 이 플랫폼의 출발점이었고, 의도한 설계였습니다.

앱이 한 번 뜬 뒤에는 사정이 달라집니다. 코드를 고칠 때마다 브라우저를 열어 버튼을 눌러야 하고, 테스트가 통과했을 때만 배포하는 흐름을 붙일 수 없습니다. 그래서 push로도 배포되는 길을 하나 더 내기로 했습니다.

## 상황

배포 한 번에는 접점이 다섯 개 있고, 모두 브라우저를 전제로 만들어져 있었습니다.

| 접점 | 하던 방식 |
| --- | --- |
| 시작 | 사람이 웹에서 버튼 클릭 |
| 설정 | 배포 폼을 처음부터 다시 채움 |
| 무엇을 | 빌더가 브랜치의 최신 커밋을 받음 |
| 인증 | 브라우저 로그인 쿠키 |
| 결과 | 웹 화면에서 확인 |

앱 하나는 서버와 정적 사이트 두 칸(슬롯)을 가질 수 있고, 두 칸이 서로 다른 저장소일 수 있습니다.

## 문제

사람 없이 배포하려면 다섯 접점이 모두 걸립니다.

- 다시 배포를 요청할 API가 없습니다.
- 폼 전체를 보내는 방식이라, 기계에 맡기면 포트나 DB 설정까지 바꿀 수 있습니다.
- 빌더가 브랜치 최신을 받으니 CI가 검사한 커밋을 가리킬 수 없고, 어떤 커밋이 떠 있는지 기록도 없었습니다.
- CI에는 로그인 쿠키가 없습니다.
- 프로그램은 화면을 볼 수 없어서, 배포가 끝났는지 알 방법이 없습니다.

길을 새로 내면 위험도 같이 생깁니다. 웹에서는 로그인한 사람이 화면을 보고 눌렀습니다. CI에서는 아무도 보지 않는 사이에 배포됩니다. 누가, 무엇을, 어디까지 배포할 수 있는지를 새로 정해야 했습니다.

## 목표와 해결 방향

목표는 push 한 번으로 배포되게 하되, 그 길로 할 수 있는 일을 그 워크플로가 돈 커밋을 그 앱에 배포하는 것 하나로 좁히는 것입니다. 저장소에 오래 사는 비밀은 두지 않습니다. 그 커밋이 테스트를 통과했는지는 사용자 워크플로의 `needs: test`가 지킵니다.

만든 것은 세 가지입니다. 서버의 재배포 API와 인증, 그것을 부르는 Go CLI, CLI를 한 줄로 쓰게 하는 GitHub Action입니다.

## 배포할 것: 빌드할 커밋을 정하는 방법

CI가 테스트한 것과 운영에 나가는 것이 같으려면, 배포 요청이 무엇을 가리킬지부터 정해야 합니다.

| 가리키는 것 | 장점 | 단점 |
| --- | --- | --- |
| 브랜치 이름 (그대로) | 바꿀 것이 없음 | 빌더가 받는 순간의 최신을 빌드. 무엇을 빌드했는지 모름 |
| 커밋 SHA | 요청한 커밋과 빌드한 커밋이 같은지 서버가 확인하고 남길 수 있음 | 빌더, core, API를 함께 바꿔야 함 |
| 이미지 digest (CI가 빌드한 이미지) | CI가 테스트한 산출물이 그대로 나감 | CI에 레지스트리 쓰기 권한을 줘야 하고, 플랫폼이 사용자 이미지를 그대로 믿어야 함 |

커밋 SHA를 골랐습니다. 빌드 환경은 플랫폼이 쥐고, 무엇을 빌드했는지는 서버가 확인할 수 있습니다.

빌더는 40자 SHA를 받으면 그 커밋 하나만 fetch하고, 받은 HEAD를 init 컨테이너 로그에 `KODEPLOY_SOURCE_SHA=` 한 줄로 찍습니다. core는 요청한 커밋과 받은 커밋을 같이 남기고, 둘이 다르면 배포 전에 실패로 끝냅니다. 이 줄은 init 컨테이너 로그에서 처음 나온 한 줄만 믿습니다. 뒤의 빌드 로그에서는 사용자 Dockerfile의 `RUN`이 같은 모양의 줄을 찍어 흉내 낼 수 있기 때문입니다.

문제가 실제로 생기는지 데모 저장소에서 재현했습니다([실행](https://github.com/yuntyu01/kodeploy-test-spring/actions/runs/45181511873)). 커밋 A의 test 잡이 도는 동안 커밋 B를 `[skip ci]`로 push하고, 앱이 내려주는 파일 본문으로 어느 커밋이 나갔는지 판정했습니다.

| 배포 | 빌드한 커밋 | 앱 응답 |
| --- | --- | --- |
| CI (A의 실행, 커밋 지정) | A | `repro-A` |
| 웹 배포 (커밋 지정 없음) | B | `repro-B` |

B는 CI의 빌드가 소스를 받기 51초 전에 올라가 있었습니다. 커밋을 고정하기 전의 빌더였다면 CI도 테스트를 거치지 않은 B를 배포했을 것입니다. 최근 CI 실행 17회에서 push부터 빌더가 소스를 받기까지는 중앙값 72초, 최대 285초였고, 이 사이에 push가 하나만 더 와도 생기는 문제입니다.

## 재배포 요청: 설정은 두고 커밋만 바꾸는 방법

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| 설정 전체를 요청으로 받기 | 웹 배포 폼과 같은 API | CI가 포트, DB, 환경변수까지 바꿀 수 있음 |
| 커밋만 받고 설정은 떠 있는 배포에서 | CI가 바꿀 수 있는 것이 커밋 하나 | 설정을 바꾸려면 웹의 설정 변경을 써야 함 |

두 번째를 골랐습니다. 재배포 API는 슬롯마다 지금 떠 있는 배포에서 설정을 다시 만들고, 커밋만 요청에서 받습니다. 같은 슬롯에서 진행 중인 빌드는 취소하고, 네트워크 문제로 같은 요청을 다시 보내면 `Idempotency-Key`로 같은 배포를 돌려줍니다.

## CI 인증: CI가 누구인지 믿는 방법

웹에서는 로그인 쿠키가 사람을 증명했습니다. CI에는 쿠키가 없어서, CI가 무엇으로 자기를 증명할지 정해야 했습니다.

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| 저장소에 토큰 저장 | 단순하고 어느 CI에서나 씀 | 오래 삶. 유출되면 회수할 때까지 쓸 수 있음. 교체를 사람이 함 |
| GitHub ID 토큰을 API마다 직접 확인 | 저장소에 비밀이 없음 | API마다 GitHub 서명 검사를 붙여야 함. 토큰의 수명과 쓰임새를 플랫폼이 정할 수 없음 |
| ID 토큰을 한 번 검사하고 CI 토큰으로 교환 | 저장소에 비밀이 없음. 수명과 쓸 수 있는 곳을 플랫폼이 정함 | 교환 API와 검사를 서버가 직접 구현 |

교환을 골랐습니다. 잡에 `id-token: write` 권한이 있으면 GitHub가 서명한 ID 토큰을 받을 수 있고, 여기에 저장소, 브랜치, 커밋 SHA, 이벤트가 들어 있습니다. core는 이 토큰을 검사하고 CI 토큰으로 바꿔 줍니다.

![GitHub Actions에서 배포까지](/images/posts/commit-pinned-ci-deploy/01.png)

CI 토큰은 일부러 약하게 만들었습니다. 아무도 보지 않는 길이라, 유출돼도 할 수 있는 일이 그 앱에 그 커밋을 다시 배포하는 것뿐이어야 하기 때문입니다.

| 항목 | CI 토큰 |
| --- | --- |
| 수명 | 15분. 기다리다 만료되면 CLI가 다시 교환 |
| 쓸 수 있는 곳 | 재배포와 상태 조회 두 라우트뿐 |
| 대상 | 교환한 앱 하나, 토큰의 커밋과 저장소 |
| 저장 | 서버에는 sha256만 남음 |
| 끄기 | 앱의 "GitHub Actions 배포 허용"을 끄면 살아 있는 토큰도 바로 만료. 기본은 꺼짐 |

교환 API는 ID 토큰이 곧 인증이라서, 서명을 확인하기 전에는 DB를 건드리지 않고 아래 순서로 하나라도 걸리면 거절합니다.

| # | 검사 | 실패 |
| --- | --- | --- |
| 1 | 서명: GitHub 공개 키, `RS256`만 | 401 |
| 2 | 발급자가 `https://token.actions.githubusercontent.com` | 401 |
| 3 | 대상이 `kodeploy` | 401 |
| 4 | 유효 시간 (시계 차이 60초 허용) | 401 |
| 5 | `jti` 1회용 | 401 |
| 6 | 앱이 있고 "GitHub Actions 배포 허용"이 켜져 있음 | 404, 403 |
| 7 | 이벤트가 `push` 또는 `workflow_dispatch` | 403 |
| 8 | 떠 있는 슬롯 중 저장소와 브랜치가 모두 토큰과 같은 슬롯이 있음 | 403 |
| 9 | 커밋이 40자 SHA | 401 |
| 10 | 앱에 워크플로 파일을 지정했으면 토큰의 워크플로가 그 파일 | 403 |
| 11 | 저장소 ID를 알면 토큰의 저장소 ID와 같음 | 403 |

10번과 11번은 운영에 올린 뒤 리뷰에서 찾은 구멍 때문에 더했습니다. 그 전에는 같은 저장소의 다른 워크플로나, `id-token: write`가 있는 서드파티 액션도 배포할 수 있었습니다. 지우고 같은 이름으로 다시 만든 저장소도 통과했습니다.

시험 앱에 `deploy.yml`을 지정하고 두 워크플로로 배포해 봤습니다. `deploy.yml`은 통과했고([실행](https://github.com/yuntyu01/kodeploy-test-spring/actions/runs/45190210577)), `other-deploy.yml`은 `403 workflow_mismatch`로 거절되어 토큰도 빌드도 남지 않았습니다([실행](https://github.com/yuntyu01/kodeploy-test-spring/actions/runs/45190977141)). CI 실행 로그에서 토큰 원문은 0건이었습니다.

## CI의 범위: 토큰 밖 슬롯을 다루는 방법

웹 배포는 앱의 모든 슬롯을 다시 빌드했고, CI 재배포도 처음에는 같은 규칙을 따랐습니다. 운영에 올린 뒤 리뷰에서 이 규칙이 CI에서는 구멍이라는 것을 찾았습니다. CI 토큰은 서버 저장소 A의 커밋을 증명하는데, 같은 앱의 정적 슬롯(저장소 B)은 브랜치 최신으로 같이 빌드돼서, B에 올려만 두고 아직 배포하지 않은 커밋이 나갈 수 있었습니다.

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| 그대로 (다른 슬롯도 브랜치 최신) | 바꿀 것이 없음 | 토큰이 증명하지 않은 커밋이 나감 |
| 저장소가 하나인 앱만 CI 허용 | 단순함 | 서버와 정적이 다른 저장소인 앱은 CI를 못 씀 |
| 다른 슬롯은 지금 떠 있는 커밋으로 고정 | 모든 앱이 CI를 쓰고, 토큰 밖 슬롯은 바뀌지 않음 | 떠 있는 커밋 기록이 없는 슬롯은 배포할 수 없음 |

세 번째를 골랐습니다. 토큰과 저장소, 브랜치가 같은 슬롯만 그 커밋으로 빌드하고, 나머지 슬롯은 지금 떠 있는 커밋으로 다시 빌드합니다. 떠 있는 커밋 기록이 없으면 `409 slot_commit_unknown`으로 멈춥니다.

![CI 재배포의 칸 고정 전과 후](/images/posts/commit-pinned-ci-deploy/02.png)

시험 앱(서버 저장소 A, 정적 저장소 B)에서 B에 배포하지 않은 커밋을 올려 두고 A에 push했습니다. B의 새 커밋은 나가지 않았고, 정적 슬롯은 떠 있던 커밋으로 빌드됐습니다. 토큰 밖 슬롯을 다시 빌드한 5건은 73~80초로, 서버 빌드와 나란히 돌아 배포를 늦추지 않았습니다.

## 결과 판정: CLI가 배포가 끝났는지 아는 방법

프로그램은 화면을 볼 수 없어서, 요청부터 상태 조회, 성공 판정까지를 대신할 것이 필요했습니다.

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| curl 스크립트 | 따로 만들 것이 적음 | 다시 교환, 시간 제한, 상태 판정을 셸로 짜야 하고, 워크플로마다 복사해야 함 |
| Go CLI (`kodeploy deploy`) | 판정 규칙을 한 곳에 두고 exit code로 알림. 바이너리 하나 | CLI를 만들고 배포해야 함 |

Go CLI를 골랐습니다. 판정은 exit code로 돌려줍니다.

| exit | 뜻 |
| --- | --- |
| 0 | 모든 슬롯이 `running`이 되고 settle 동안 문제가 없음 |
| 1 | `failed`가 하나라도 있음 |
| 2 | 요청이 잘못됨 (400, 422, 되풀이되는 409) |
| 3 | 실패 없이 `cancelled`가 있음 (더 새 배포가 이어받음) |
| 4 | 시간 초과 |
| 125 | 인증, 권한, 연결 문제 |
| 130 | 중단 |

settle은 서버 빌드가 `running`이 된 뒤 더 기다리는 시간입니다. 서버는 그 60초 동안 앱 Pod를 더 지켜보고, 재시작이나 OOM이 있으면 배포를 `failed`로 바꿉니다. settle을 0초로 두면 시작 직후 죽는 앱을 성공으로 끝냅니다.

CLI가 기다리는 숫자는 운영 기록의 배포 43회에 맞춰 봤습니다. 판정 기준은 결과를 보기 전에 정했습니다.

| 숫자 | 기준 | 결과 | 판정 |
| --- | --- | --- | --- |
| CI 토큰 15분 | 15분 넘게 기다린 배포가 5% 이하 | 대기 중앙값 179초, 최대 491초. 다시 교환 0% | 맞음 |
| 시간 제한 25분 | 최대 대기와 서버 상한(약 23분)이 25분 미만 | 최대 8분 11초 | 맞음 |
| settle 60초 | 서버가 지켜보는 시간과 같음 | 같음. `running` 뒤 실패 1건(2.3%) | 맞음 |
| 조회 간격 (2초에서 10초까지 늘림) | 요청이 2초 고정의 절반 이하이고, 감지 지연이 10초 고정보다 짧음 | 요청 28%, 지연 4.6초 (10초 고정 4.3초) | 안 맞음 |

![운영 기록으로 본 대기 시간과 폴링](/images/posts/commit-pinned-ci-deploy/04.png)

settle이 잡은 1건은 시험 앱의 서버가 `running`이 된 뒤 시작 코드에서 죽은 경우입니다. settle이 0초였다면 CLI는 이 배포를 성공으로 끝냈을 것입니다. 조회 간격은 상태가 `running`으로 바뀌기까지 보통 1분쯤 걸려서, 늘려 가는 간격이 금방 10초에 닿았습니다. 10초 고정이면 지연은 같고 요청은 23% 줄어서, 다음에 바꿀 값으로 남겼습니다.

## 액션 배포: 받은 CLI를 믿는 방법

워크플로에서는 composite 액션 [kodeploy/deploy-action](https://github.com/kodeploy/deploy-action)이 CLI를 내려받아 실행합니다.

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| 확인 없이 내려받기 | 단순함 | 릴리스가 바뀌면 그대로 실행 |
| 릴리스의 체크섬 파일로 확인 | 흔히 쓰는 방식 | 바이너리와 체크섬을 함께 바꾸면 막지 못함 |
| 기본 버전의 sha256을 액션 저장소에 커밋 | 릴리스를 바꿔도 sha256이 맞지 않으면 거절 | 버전을 올릴 때마다 sha256도 고쳐야 함 |

세 번째를 골랐습니다. 입력값은 셸에 바로 넣지 않고 env로만 넘깁니다. 사용자 워크플로는 액션을 커밋 SHA로 고정해서 씁니다([실행](https://github.com/yuntyu01/kodeploy-test-spring/actions/runs/45039673064)).

```yaml
deploy:
  needs: test
  runs-on: ubuntu-latest
  permissions:
    id-token: write
    contents: read
  steps:
    - uses: kodeploy/deploy-action@678ee39b122c1242a5b12a22c1431a187205fd49 # v1.0.0
      with:
        app: ${{ vars.KODEPLOY_APP_ID }}
```

## 겹치는 배포: 같은 브랜치에 push가 잇달아 올 때

같은 브랜치에 push가 잇달아 오면 deploy 잡이 겹칩니다. 서버는 같은 슬롯에서 진행 중인 빌드를 취소하고, 그 빌드를 기다리던 CLI는 exit 3(밀림)으로 끝납니다. GitHub 쪽은 워크플로의 `concurrency`로 정합니다.

| 안 | 설정 | 장점 | 단점 |
| --- | --- | --- | --- |
| (a) 차례로 | `cancel-in-progress: false` | 앞 커밋도 끝까지 배포 | 마지막 커밋이 앞 배포를 다 기다림 |
| (b) 앞 잡 취소 | `cancel-in-progress: true` | 마지막 커밋이 빨리 나감 | 앞 잡이 취소로 표시됨 |
| (c) 설정 없음 | 없음 | 마지막 커밋이 빨리 나감 | 앞 빌드가 서버에서 밀려 빌드 시간이 버려짐 |

처음에는 돌고 있는 배포를 끊지 않는 (a)가 안전하다고 보고 그렇게 두었습니다. 두 번째 커밋이 얼마나 늦어지는지는 재지 않았습니다.

세 안을 실측했습니다. 커밋 A를 push하고 약 40초 뒤 커밋 B를 push하는 실험을 안마다 2번 했습니다. 기준은 B를 push한 뒤 B가 `running`이 되기까지가 (a)보다 30% 이상 짧고 실패나 빨간 잡이 없으면 바꾸고, 둘 다 해당하면 더 짧은 안을 고르는 것이었습니다.

| 안 | B push부터 B `running`까지 (평균) | 취소된 빌드 | 잡 결과 | A가 운영에 |
| --- | --- | --- | --- | --- |
| (a) | 465.8초 | 0개 | 모두 초록 | 나감 |
| (b) | 271.2초 | 1개 | A 잡 회색 | 안 나감 |
| (c) | 257.1초 | 2개 | 모두 초록 | 안 나감 |

![concurrency 세 안](/images/posts/commit-pinned-ci-deploy/05.png)

(b)와 (c) 모두 기준을 넘었고, 더 짧은 (c)로 바꿔 deploy 잡에서 `concurrency`를 뺐습니다. 둘의 차이 14초는 회차 사이 차이와 비슷한 크기라서, 미리 정한 기준이 없었다면 가르기 어려웠을 것입니다.

## 한계 및 회고

- 워크플로 지정은 선택입니다. 앱에 워크플로 파일을 지정하지 않으면 그 저장소와 브랜치의 어느 워크플로든 배포할 수 있습니다. 지정해도 파일 경로만 보므로, 배포 브랜치에 push할 수 있는 사람은 그 파일을 고칠 수 있습니다. 배포 브랜치 보호가 다음 일입니다.
- 플랫폼이 소스로 다시 빌드합니다. CI가 만든 이미지를 쓰지 않아서 빌드 시간이 한 번 더 들고, CI가 테스트한 산출물과 운영 이미지는 같은 커밋의 다른 빌드입니다.
- CI는 지금 GitHub Actions만 지원합니다. 교환 API가 확인하는 발급자와 항목 이름이 GitHub의 ID 토큰에 맞춰져 있습니다. GitLab CI 같은 다른 CI를 받으려면 발급자 설정과 항목 매핑을 더해야 합니다.
- CLI의 인증은 지금 GitHub Actions의 OIDC 교환뿐입니다. 사람이 터미널에서 로그인해 쓰는 방식은 아직 지원하지 않습니다.
- 서버는 마지막 요청을 살릴 뿐 커밋의 앞뒤를 보지 않습니다. 앞 커밋의 test 잡이 더 늦게 끝나면 앞 커밋이 남습니다.
- 실측 표본이 작습니다. 겹치는 배포는 안마다 2회, 운영 기록은 배포 43회입니다.

웹의 규칙을 CI에 그대로 가져왔다가 구멍이 났습니다. 웹 배포가 앱의 모든 슬롯을 다시 빌드하는 것은 사람이 화면을 보고 누르니 문제가 없었지만, 아무도 보지 않는 CI 길에서는 토큰이 증명하지 않은 커밋을 내보내는 구멍이 됐습니다. 워크플로 검사가 빠졌던 것도 같은 이유입니다. 사람이 보고 누르는 길과 아무도 보지 않는 길은 같은 규칙을 쓸 수 없었습니다. 판정 기준을 미리 적어 둔 것은 도움이 됐습니다. (b)와 (c)의 14초 차이도 기준이 있어서 고를 수 있었고, 직관으로 고른 조회 간격이 기록상 이득이 없다는 것도 기준 덕분에 그대로 받아들일 수 있었습니다.

전체 흐름과 API 형식은 [아키텍처 07 - CI/CD](/architecture/07-cicd.html)에 정리했습니다.
