> **요약**
>
> - API 서버(core)가 Pod exec 하나로 웹 터미널, DB 콘솔, 덤프, 복원을 처리했습니다. exec는 할 수 있는 일이 정해지지 않은 권한이라, core가 탈취되면 테넌트 컨테이너에서 모든 명령을 실행할 수 있었습니다.
> - exec를 core에서 빼서 Go 게이트웨이에 맡겼습니다. core의 토큰만 유출된 경우에는 컨테이너 안에서 명령을 실행할 수 없게 됐고, core가 통째로 탈취되는 경우는 대상과 시작 명령, 세션 수와 시간으로 좁혔습니다. core와 게이트웨이 사이는 테넌트별 인증서로 TLS를 걸었습니다.
> - 게이트웨이를 둘 자리는 권한으로 골랐습니다. 하나로 합치면 전역 exec가 옮겨갈 뿐이고, 요청이 올 때 만들면 exec보다 센 Pod 생성 권한이 필요했습니다. 평소 0개로 두는 안은 첫 연결이 1.5~2.8초 걸려 기준 1초를 넘었습니다.
> - 테넌트마다 하나씩 상주시키고 core의 `pods/exec`를 회수했습니다. 게이트웨이는 하나에 10MiB 안팎입니다.

## 배경

[지난 글](/blog/rbac-rolebinding-vap/)에서 API 서버(core)의 권한을 앱 네임스페이스 안으로 가뒀습니다. 그때 끝까지 남은 권한이 Pod exec였고, 이 글은 그 exec를 core에서 빼낸 과정입니다. 글에서 테넌트는 앱마다 하나인 네임스페이스를 말합니다.

## 상황

core는 사용자가 웹에서 쓰는 기능 네 가지를 모두 K8s API의 Pod exec로 처리했습니다.

| 기능 | 하던 방식 |
| --- | --- |
| 웹 터미널 (앱, DB, Redis) | tty exec를 WebSocket으로 중계 |
| DB 콘솔, 표 탐색 | `mysql`, `psql`을 exec |
| 덤프 | `mysqldump`를 exec |
| 복원 | exec로 업로드 파일을 Pod 안 임시 파일에 쓰고, 다시 exec해서 그 파일을 `mysql`로 적재 |

DB 비밀번호는 core가 Secret에서 읽어 `mysql -p<비밀번호>`처럼 명령에 넣었습니다.

## 문제: 할 수 있는 일이 정해지지 않은 권한

앞의 두 글에서 core의 권한을 두 번 줄였습니다. 워크로드를 쓰는 권한은 [Argo CD로 넘겼고](/blog/argocd-declarative-deploy/), 남은 권한은 [RoleBinding과 VAP로](/blog/rbac-rolebinding-vap/) 테넌트 네임스페이스 안에 가뒀습니다. 그 뒤 테넌트 롤에 남은 권한은 이렇습니다.

| 권한 | 할 수 있는 일 |
| --- | --- |
| namespaces delete | 그 앱의 네임스페이스 삭제 |
| secrets get, create, update, delete | 이름을 아는 Secret 읽고 쓰기 |
| persistentvolumeclaims create | 볼륨 만들기 |
| pods list, pods/log get | Pod 목록과 로그 읽기 |
| pods/exec get, create | 어느 컨테이너에서든 모든 명령 실행 |

위의 네 줄은 할 수 있는 일이 이름에 적혀 있습니다. exec만 다릅니다. 컨테이너 안에서 명령을 실행할 수 있으면, 그 컨테이너가 할 수 있는 일은 모두 할 수 있습니다.

- DB 컨테이너에서는 DB 셸이 열려서, 데이터를 읽고 바꿀 수 있습니다.
- 앱 컨테이너에서는 환경변수와 파일을 읽고, 실행 중인 프로세스를 바꿀 수 있습니다.
- 명령은 그 Pod의 네트워크 위치에서 실행되므로, 네트워크 정책이 그 Pod에 허용한 곳에는 모두 닿습니다.
- kube-apiserver의 감사 로그에 남는 것은 exec 연결을 연 요청까지이고, 열린 셸 안에서 친 명령은 남지 않습니다.

그래서 앞의 두 작업에는 exec라는 빈틈이 남습니다. 워크로드를 쓰는 권한은 뺐지만, exec로는 실행 중인 컨테이너 안을 바꿀 수 있습니다. 닿는 범위는 테넌트 안으로 좁혔지만, 그 안에서 할 수 있는 일은 exec 하나 때문에 줄지 않습니다.

DB도 같습니다. core는 Secret에서 DB 비밀번호를 읽을 수 있지만, 네트워크 정책이 core에서 테넌트 DB로 가는 연결을 막고 있어서 비밀번호만으로는 DB에 닿지 못합니다. core가 DB에 닿는 길은 exec뿐이었습니다.

core는 외부 요청을 받는 서버라서, 탈취되면 이 권한이 모든 테넌트에서 그대로 쓰입니다. core의 토큰만 유출돼도 같습니다.

## 목표와 해결 방향

목표는 core가 K8s 권한으로 직접 exec하던 것을 없애고, 게이트웨이를 거쳐서만 요청하게 하는 것입니다. 게이트웨이는 exec 권한을 갖고 core 대신 exec를 해 주는 별도 Pod입니다.

core는 앞으로도 사용자 대신 터미널과 DB 작업을 요청해야 하고, 게이트웨이가 받는 작업에는 셸 열기도 있습니다. 그래서 core가 탈취됐을 때의 피해가 0이 되지는 않습니다. 줄어드는 것은 세 가지입니다.

- core의 토큰만 유출된 경우에는 컨테이너 안에서 명령을 실행할 수 없습니다.
- 대상 컨테이너와 시작 명령이 고정됩니다.
- 모든 세션이 게이트웨이를 지나서, 수와 시간이 제한되고 기록됩니다.

정할 것은 세 가지였습니다. 게이트웨이가 Pod에 닿는 길, 게이트웨이를 구하는 방법, 게이트웨이를 두는 자리입니다.

## 게이트웨이가 Pod에 닿는 길: SSH vs exec

Pod 안에서 명령을 실행하는 길은 두 가지입니다.

| 길 | 장점 | 단점 |
| --- | --- | --- |
| Pod에 SSH 서버를 두고 직접 연결 (SSH 프록시) | 바이트가 kube-apiserver를 지나지 않음 | 대상 컨테이너에 SSH 서버가 있어야 함. Pod마다 열린 포트와 키가 하나씩 늘어남 |
| K8s exec | 대상 컨테이너에 따로 설치할 것이 없음. 권한이 K8s RBAC 하나로 정해짐 | 모든 바이트가 kube-apiserver와 kubelet을 지남 |

KoDeploy가 돌리는 것은 사용자가 빌드한 이미지와 공식 DB 이미지입니다. 그 안에 SSH 서버를 넣으려면 남의 이미지를 바꿔야 하고, 사이드카로 붙이면 셸이 앱 컨테이너 밖에서 열립니다. 그래서 원래 쓰던 exec를 유지했습니다. 플랫폼이 이미지를 직접 만드는 작업용 Pod였다면 SSH 쪽도 고를 만했습니다. exec의 대가인 kube-apiserver 경유는 한계에서 다시 다룹니다.

## 게이트웨이를 구하는 방법: 오픈소스 vs 직접 구축

exec를 대신 해 주는 게이트웨이는 오픈소스로도 있습니다. SSH 접속을 받아 exec로 바꿔 주는 도구입니다. 요청을 받아 대신 exec한다는 구조는 같고, 다른 것은 앞문과 받는 작업입니다.

| 안 | 장점 | 단점 |
| --- | --- | --- |
| 오픈소스 게이트웨이 (SSH를 받아 exec로 바꿔 줌) | 직접 만들 것이 적음 | 앞문이 SSH라 브라우저 앞에 변환 서버와 키 관리가 따로 필요. 받는 작업이 셸뿐이라 SQL 실행, 덤프, 단계가 있는 복원은 따로 만들어야 함 |
| 직접 구축 | 브라우저 앞문(티켓)과 DB 작업을 한 바이너리에 넣을 수 있음 | 인증과 중계 코드를 직접 책임져야 함 |

오픈소스를 쓰지 않은 이유는 기능입니다. 브라우저가 붙을 앞문이 없고, core가 요청하는 DB 작업이 없습니다. 둘을 따로 만들어 붙이면 구성 요소만 늘어나서 직접 만들었습니다. 셸을 여는 작업은 오픈소스와 다르지 않습니다.

전부 새로 만든 것은 아닙니다. exec 연결은 K8s 공식 라이브러리인 client-go를 쓰고, 서명은 표준 HMAC-SHA256을 씁니다. 직접 짠 것은 받는 작업의 목록, 티켓, 복원 단계입니다.

## 게이트웨이를 두는 자리: 어디에, 몇 개를, 언제

게이트웨이를 두는 방법 네 가지를 비교했습니다. 기준은 순서대로 권한, 첫 연결, 메모리입니다.

| 배치 | exec가 닿는 범위 | exec 말고 새로 필요한 권한 | 첫 연결 | 평소 메모리 |
| --- | --- | --- | --- | --- |
| 클러스터에 하나 | 모든 테넌트 | 없음 | 바로 | 1개분 |
| 테넌트마다, 요청이 올 때 생성 | 그 테넌트 | core에 Pod 생성 | 재지 않음 (권한에서 탈락) | 0 |
| 테넌트마다, 평소 0개 | 그 테넌트 | 깨우는 쪽에 scale 권한 또는 KEDA | 1.51~2.78초 | 0 |
| 테넌트마다, 상주 | 그 테넌트 | 없음 | 0.10~0.11초 | 1개에 RSS 약 9MiB |

클러스터에 하나를 두면 그 게이트웨이에 모든 테넌트의 exec가 필요합니다. 전역 exec가 core에서 게이트웨이로 옮겨갈 뿐이라 뺐습니다.

요청이 올 때 게이트웨이 Pod를 만드는 안은 메모리도 아끼고 exec도 빼는 안처럼 보였습니다. 하지만 만드는 쪽인 core에 Pod 생성 권한이 필요합니다. Pod 생성 권한이 있으면 원하는 ServiceAccount와 Secret을 마운트한 Pod를 띄워 그 토큰과 Secret을 그대로 쓸 수 있습니다. exec를 빼려다 exec보다 센 권한을 주게 되므로, core와 게이트웨이 모두 Pod 생성 권한은 주지 않기로 하고 이 안도 뺐습니다.

남은 것은 평소 0개와 상주입니다. 평소 0개는 요청이 올 때 게이트웨이를 깨우는 쪽이 따로 있어야 합니다. core에 scale 권한을 주면 지금까지 권한을 줄여 온 방향과 반대가 되고, KEDA를 쓰면 클러스터에 구성 요소를 하나 더 들여 관리해야 합니다. 어느 쪽이든 Argo CD가 replicas를 되돌리지 않게 동기화에서 빼 두는 설정도 필요합니다. 반대로 상주 비용은 작았습니다. 게이트웨이 1개가 RSS 약 9MiB였습니다. 그래서 평소 0개를 고를 이유는 첫 연결이 충분히 빠를 때뿐이라고 보고, 첫 연결이 1초 넘게 늦어지면 쓰지 않기로 측정 전에 정했습니다.

시험 앱에서 게이트웨이를 0개에서 1개로 올리고, 첫 SQL이 성공하기까지를 쟀습니다. 1.51\~2.78초로, 미리 떠 있을 때(0.10\~0.11초)보다 매번 1.4초 이상 늦어져 기준 1초를 넘었습니다. 이미지가 이미 있는 노드에서 잰 값이고, 이미지를 처음 받는 노드에서는 Pod가 Ready가 되는 데만 6초가 걸렸습니다.

닿는 범위가 테넌트 안이고, 새 권한이 필요 없고, 바로 연결되는 것은 상주뿐입니다. 그래서 테넌트마다 게이트웨이 1개를 상주시키기로 정했습니다.

## 게이트웨이와 두 문

`kodeploy-exec`는 Go와 client-go로 만든 바이너리 하나이고, 테넌트 네임스페이스마다 하나씩 뜹니다. 권한은 자기 네임스페이스의 Pod 목록과 `pods/exec`뿐이고, Secret은 읽지 못합니다. 문은 두 개이고, 문마다 받는 작업이 정해져 있습니다.

| 문 | 들어오는 쪽 | 받는 작업 |
| --- | --- | --- |
| 공개 문 (8080) | 브라우저 (Envoy 경유) | 앱 셸, DB 콘솔, Redis 콘솔 |
| 내부 문 (8081) | core | 티켓 발급, SQL 실행, 표 탐색, 덤프, 복원 |

core가 탈취되면 이 표에 있는 작업을 요청할 수 있습니다. 셸 열기가 들어 있으므로 그 컨테이너 안에서는 모든 명령을 실행할 수 있습니다. 달라진 것은 대상이 앱, DB, Redis 컨테이너로 고정되고 시작 명령도 정해져 있다는 점, 그리고 연결이 게이트웨이의 제한과 기록을 지난다는 점입니다. 터미널은 15분 동안 입력이 없으면 닫히고 최대 2시간이며, 동시 세션은 공개 문 3개, 내부 문 4개까지입니다.

게이트웨이 계정 자체는 exec를 갖고 있으므로, 그 계정으로 다른 Pod를 띄우지 못하게 ValidatingAdmissionPolicy로 Pod 모양(컨테이너 하나, 이미지 digest 고정)을 묶었습니다.

## 공개 문: 브라우저가 게이트웨이에 붙는 방법

터미널의 입출력이 core를 지나면 core가 모든 세션의 내용을 볼 수 있습니다. 그래서 브라우저가 게이트웨이에 직접 붙게 했습니다. 그러려면 브라우저가 게이트웨이에 자기를 증명해야 하는데, 게이트웨이는 누가 이 앱의 주인인지 모릅니다. 방법은 세 가지가 있습니다.

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| 로그인 쿠키를 게이트웨이가 직접 확인 | 티켓을 따로 만들 필요가 없음 | 게이트웨이가 세션과 앱 소유 정보를 조회해야 함. 로그인 쿠키가 테넌트 네임스페이스의 Pod까지 가서, 게이트웨이가 뚫리면 세션이 넘어감 |
| JWT (정보와 서명을 담은 토큰. core가 서명) | 게이트웨이는 서명만 확인하면 되고, 메모리에 둘 것이 없음 | 수명 안에서는 끊을 수 없음. 한 번만 쓰게 하려면 결국 쓴 토큰을 메모리에 남겨 둬야 함. 서명 키를 core와 게이트웨이가 나눠 가져야 함 |
| 난수 티켓 (아무 정보도 없는 난수. 게이트웨이가 만들어 메모리에 둠) | 한 번 쓰면 지워서 끝. 서명 키를 나눠 가질 필요가 없음 | 게이트웨이가 발급한 티켓을 메모리에 들고 있어야 함 |

티켓을 만드는 곳과 확인하는 곳이 같은 게이트웨이라서, 발급한 티켓을 자기 메모리에 적어 두고 바로 찾아보면 됩니다. 메모리에 들고 있어야 한다는 단점은 이런 일회용 연결에서는 오히려 장점입니다. 들고 있으니 쓰는 순간 지워서 한 번만 쓰게 할 수 있고, JWT로 한 번만 쓰게 하려면 결국 해야 하는 일을 처음부터 하는 셈입니다. 게이트웨이가 다시 뜨면 티켓이 사라지지만, 30초짜리라 다시 받으면 됩니다. 그래서 난수 티켓(32바이트, 30초, 1회용)을 골랐습니다. 사용자 확인은 core가 하고, 게이트웨이는 core가 받아 간 티켓만 확인합니다. 연결 순서는 이렇습니다.

![웹 터미널 연결 순서](/images/posts/tenant-exec-gateway/02.png)

| 단계 | 하는 일 | 이유 |
| --- | --- | --- |
| ① 티켓 요청 | 브라우저가 core에 티켓을 요청합니다. core는 로그인 세션과 Origin을 보고, 요청한 사람이 앱 주인인지 확인합니다 | 이 앱의 주인이 누구인지 아는 곳은 core뿐입니다. 게이트웨이는 사용자를 모릅니다 |
| ② 서명한 요청 | core가 서명한 요청을 게이트웨이 내부 문에 보냅니다. 게이트웨이는 32바이트 난수를 만들어 돌려주고, 자기 메모리에는 sha256만 둡니다 | 만드는 곳과 확인하는 곳이 같아서 서명 키를 나눠 가질 필요가 없습니다. 원문을 두지 않아서 메모리 내용이 유출돼도 티켓으로 쓸 수 없습니다 |
| ③ 티켓 전달 | core가 티켓과 접속 주소를 브라우저에 넘깁니다. 티켓은 30초 안에 한 번만 쓸 수 있습니다 | 유출돼도 쓸 수 있는 시간이 짧고, 한 번 쓰면 끝납니다 |
| ④ WebSocket 연결 | 브라우저가 게이트웨이 공개 문으로 직접 WebSocket을 엽니다. 티켓은 `Sec-WebSocket-Protocol` 헤더에 넣고, Envoy는 Cookie 헤더를 지우고 넘깁니다 | 터미널 입출력이 core를 지나지 않습니다. URL에 넣으면 접근 로그와 브라우저 기록에 남고, 브라우저는 WebSocket에 Authorization 헤더를 붙일 수 없습니다. 로그인 쿠키는 게이트웨이에 필요 없습니다 |
| ⑤ 티켓 확인 후 지움 | 게이트웨이가 Origin을 확인하고, 티켓을 찾아 그 자리에서 지웁니다 | 브라우저에서 온 연결은 허용한 사이트에서 연 것만 받습니다. 지우기 때문에 같은 티켓을 두 번 쓸 수 없습니다 |
| ⑥ exec | 게이트웨이가 자기 계정으로 대상 컨테이너에 exec를 엽니다 | exec 권한은 게이트웨이에만 있고, core에는 없습니다 |
| ⑦ 바이트 그대로 중계 | 브라우저와 컨테이너 사이의 바이트를 그대로 넘깁니다. 채널 번호는 K8s exec와 같습니다 | 게이트웨이가 내용을 해석하지 않아서 한글이 깨지지 않고, 창 크기도 K8s의 창 크기 채널로 그대로 갑니다 |

어느 방법이든 바뀌지 않는 것이 있습니다. 사용자를 확인하고 연결 자격을 내주는 곳은 core라서, core가 탈취되면 연결할 자격을 얻을 수 있습니다. 서명을 비대칭키로 바꾸거나 키를 Vault에 넣어도 이 점은 같습니다.

## 내부 문: core가 게이트웨이를 부르는 방법

core가 게이트웨이를 부를 때 자기가 core임을 증명하는 방법은 네 가지가 있습니다.

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| 네트워크 정책만 (서명 없음) | 가장 단순함 | 정책이 빠지거나 잘못 걸리면 누구나 부를 수 있음 |
| core의 ServiceAccount 토큰을 보내고 게이트웨이가 K8s에 확인 | K8s가 신원을 보증함 | core의 토큰이 테넌트 Pod로 감. 게이트웨이에 토큰 확인 권한이 더 필요 |
| mTLS (인증서로 서로 확인) | 신원 확인과 암호화를 함께 함 | 인증서를 발급하고 교체할 구성 요소가 필요 |
| HMAC 서명 (테넌트마다 다른 공유 키) | 표준 라이브러리만으로 됨. 빌더 요청에 이미 쓰던 규칙. 한 테넌트의 키가 유출돼도 다른 테넌트는 못 부름 | 키가 K8s Secret에 있고 core의 토큰으로 읽을 수 있어서, 토큰이 유출되면 키도 유출됨. 연결은 암호화되지 않음. 60초 안의 재전송은 못 막음 |

HMAC을 골랐습니다. 이미 쓰던 규칙이고 새 구성 요소가 필요 없습니다.

키는 core가 테넌트 네임스페이스를 만들 때 32바이트 난수로 만들어, 그 네임스페이스의 K8s Secret(`kodeploy-exec-hmac`)에 넣습니다. core는 이 Secret을 읽어 서명하고, 게이트웨이는 같은 Secret을 읽기 전용으로 받아 서명을 확인합니다. core가 이 Secret을 읽을 수 있다는 것은 core의 토큰을 손에 넣은 쪽도 읽을 수 있다는 뜻이라, 토큰이 유출되면 키도 함께 유출됩니다.

키 유출과 재전송은 네트워크 정책으로 덮습니다. 유출된 키로 서명하든 가로챈 요청을 다시 보내든, 결국 8081에 연결해야 하는데 8081은 core Pod에서 온 연결만 받습니다. 평문은 네트워크 정책으로 덮이지 않습니다. 정책은 누가 연결할지를 정할 뿐, 지나가는 트래픽을 감추지는 않습니다. 그래서 평문은 따로 TLS로 막았습니다(다음 절). 내부 문은 HMAC 서명과 네트워크 정책 두 겹으로 지키고, 그 위에 TLS를 씌웠습니다.

| 겹 | 막는 것 | 혼자서는 못 막는 것 |
| --- | --- | --- |
| HMAC 서명 (테넌트마다 다른 키) | 키가 없는 쪽의 요청, 다른 테넌트의 키로 서명한 요청 | core의 토큰이 유출돼 그 토큰으로 키를 읽은 경우 |
| 네트워크 정책 (core Pod에서 온 연결만) | core Pod가 아닌 모든 곳에서 온 연결. 같은 네임스페이스의 사용자 앱도 포함 | core Pod 안에서 보낸 요청 |

두 겹이 서로의 빈틈을 메웁니다. 토큰이 유출돼 키를 읽어도 core Pod가 아니면 연결이 안 되고, 네트워크 정책이 빠지거나 잘못 걸려도 키가 없으면 서명을 만들 수 없습니다. 둘 다 뚫리는 것은 core Pod 자체가 탈취된 경우뿐이고, 그 경우는 한계에 적었습니다.

서명에는 시각이 들어가서 ±60초 안의 요청만 받습니다. 가로챈 요청을 나중에 다시 보내도 60초가 지나면 거절됩니다. 그 안에 다시 보내는 것까지 막는 일회용 값(nonce)은 두지 않았습니다.

네트워크 정책은 두 가지로 걸 수 있었습니다.

| 네트워크 정책 | 장점 | 단점 |
| --- | --- | --- |
| K8s NetworkPolicy | 표준이라 차트에 쓰기 쉬움 | Calico가 order 1000으로 처리해서, 같은 네임스페이스끼리 모든 포트를 여는 기존 테넌트 정책(order 100)보다 늦게 봄. 같은 네임스페이스의 앱을 막지 못함 |
| Calico NetworkPolicy, order 50 | 기존 정책보다 먼저 결정 | Calico에 묶임 |

같은 네임스페이스의 앱을 막으려면 기존 정책보다 먼저 봐야 해서 Calico order 50을 골랐습니다. 8080은 Envoy, 8081은 core Pod, 9090은 지표 수집과 kubelet만 받고, 나가는 쪽은 kube-apiserver와 DNS만 엽니다.

## 내부 문 암호화: core와 게이트웨이 사이를 TLS로 감싸는 방법

처음에는 내부 문이 평문 HTTP였습니다. 노드 사이 트래픽은 Calico IPIP로 OCI 네트워크를 지나는데 이 구간에 암호화가 없어서, SQL 결과, 덤프, 복원 파일이 그대로 지나갔습니다.

| 방법 | 가려 주는 범위 | 대가 |
| --- | --- | --- |
| 내부 문에 TLS | core와 게이트웨이 사이 | core와 게이트웨이 코드 수정. 인증서를 나눠 주고 바꾸는 절차가 필요 |
| Calico WireGuard | 노드 사이를 지나는 모든 Pod 트래픽 | 클러스터 네트워크 설정을 바꿔야 함. 같은 노드 안의 트래픽은 그대로 |
| 서비스 메시 (mTLS 자동) | 메시에 넣은 모든 Pod | Pod마다 사이드카가 붙어서 노드 3대 클러스터에는 무거움 |

내부 문 TLS를 먼저 골랐습니다. core는 이미 테넌트 네임스페이스를 만들 때 HMAC 키를 Secret으로 넣고 있어서, 같은 자리에서 테넌트별 인증서를 하나 만들어 같이 넣으면 됩니다. 새 구성 요소가 필요 없습니다.

인증서는 테넌트마다 자체 서명으로 만들고, core는 그 테넌트의 인증서 하나만 믿습니다. 클러스터 CA 하나로 발급하면 CA 키를 쥔 core가 아무 인증서나 만들 수 있고, cert-manager는 구성 요소가 하나 늘어서 고르지 않았습니다. 게이트웨이는 인증서 파일이 바뀌면 다음 연결부터 새 인증서를 내놓습니다.

옮기는 동안 내부 문이 끊기지 않게, 게이트웨이는 같은 포트에서 첫 바이트로 TLS와 평문을 가려 둘 다 받게 했습니다. TLS 연결은 핸드셰이크 레코드(0x16)로 시작하고, 평문 HTTP는 메서드 글자로 시작하기 때문입니다. core 배포와 인증서 채우기, 게이트웨이 교체, core가 TLS로 부르기, 평문 막기 순서로 옮겼습니다. 마지막에 8개 테넌트 모두 평문 연결은 응답 없이 끊기고, TLS로는 SQL이 실행되는 것을 확인했습니다.

## DB 복원

업로드를 `mysql`에 바로 흘려 넣으면 exec 한 번으로 끝나지만, 적재 전에 파일이 맞는지 알 수 없고 중간에 끊기면 DB가 어디까지 바뀌었는지 모릅니다. 그래서 Pod 안에 파일로 먼저 받아 크기와 해시를 확인하고, 지금 DB를 백업한 뒤 적재합니다. 실패하면 백업으로 되돌리고, 되돌리기까지 실패하면 백업을 남겨 두고 다음 복원을 거절합니다. 대가는 시간입니다. 같은 복원이 0.88초에서 4.04초로 늘었습니다.

## 적용 결과

옛 경로를 바로 지우지 않고, 새 경로를 옆에 둔 채 운영의 앱 하나(카나리)에서 먼저 켰습니다. 같은 요청을 옛 경로와 새 경로에 보내 비교하고, 실패 상황도 일부러 만들었습니다.

| 확인한 것 | 결과 |
| --- | --- |
| SQL 6건, 표 탐색 4건 | 옛 경로와 차이 없음 |
| 덤프 | 둘 다 310,990바이트, diff 0줄 |
| 복원 | 표별 행 수 같음 |
| 웹 터미널 | 한글 입력, 창 크기, Redis `PONG` 정상. MySQL 콘솔 한글 깨짐은 `LANG=C.UTF-8`로 고침 |
| 복원 실패 | 업로드 중 끊으면 DB 그대로, 해시가 틀리면 upload 단계에서 실패 |
| 동시 세션 | 상한(3개)을 넘는 네 번째 연결은 `4429`로 거절 |
| 같은 네임스페이스의 앱에서 게이트웨이로 | 세 포트 모두 연결 시간 초과. 대조로 같은 Pod에서 MySQL 3306은 연결됨 |

결과가 같아서 전체 테넌트로 넓혔고, 그다음 옛 경로를 지우고 core의 `pods/exec`를 회수했습니다.

회수 확인에는 `kubectl auth can-i`를 쓰지 않았습니다. exec 연결은 GET 요청으로 열리지만 인가는 create로 합니다. 그래서 get만 남겨 보니 can-i는 허용이라고 답했는데 실제 연결은 `403`이었습니다. can-i의 답과 실제 결과가 다를 수 있어서, core Pod 안에서 실제 exec 요청을 보내 확인했습니다. 회수 전에는 `ALLOWED`, 회수 후에는 `403`이었습니다.

| | 전 | 후 |
| --- | --- | --- |
| core의 Pod exec | 있음 | 없음 |
| core의 토큰만 유출되면 | 테넌트 컨테이너에서 모든 명령 | 컨테이너 안에서 명령을 실행할 수 없음 |
| core가 통째로 탈취되면 | 어느 Pod에서든 모든 명령 | 게이트웨이가 받는 작업만 (셸 열기 포함) |
| core 테넌트 롤 권한 | 10개 | 8개 |
| core와 게이트웨이 사이 | 평문 HTTP | TLS 1.3 (테넌트별 인증서) |
| 늘어난 것 | | 게이트웨이 8개, 하나에 working set 8.8~20.2MiB |

## 한계 및 회고

- core가 통째로 탈취되면 티켓을 받아 셸을 열 수 있고, 그 컨테이너 안에서는 모든 명령을 실행할 수 있습니다. SQL 실행도 클라이언트의 셸 명령(`\!`)으로 DB 컨테이너의 셸에 닿는 것을 시험 앱에서 확인했습니다. 막은 것은 토큰만 유출된 경우이고, 전체 탈취는 좁혔을 뿐입니다. `\!`를 막는 것이 다음 일입니다.
- Envoy에서 게이트웨이로 가는 공개 문(터미널 입출력)은 아직 클러스터 안에서 평문입니다. 내부 문은 TLS로 감쌌지만, 공개 문 구간까지 덮으려면 Calico의 WireGuard로 노드 사이 트래픽 전체를 암호화하는 것을 검토합니다. 내부 문 인증서는 10년짜리이고, 바꾸는 일은 Secret을 지우고 다시 만드는 수동 절차입니다.
- core는 여전히 앱의 네임스페이스를 지울 수 있습니다. exec 회수로 줄어든 것은 컨테이너 안에서 할 수 있는 일입니다.
- exec 바이트는 여전히 kube-apiserver를 지납니다. 200MiB 복원이 master 메모리 3.6GB에서는 실패했고, 6GB로 늘린 뒤 통과했습니다.
- 테넌트마다 메모리 요청 64Mi가 상주합니다. 앱이 12개쯤 되면 워커 메모리의 5%에 닿습니다.

권한을 줄이는 안을 고를 때는 그 안을 하려면 누가 어떤 권한을 새로 가져야 하는지부터 따져야 했습니다. 요청이 올 때 Pod를 만드는 안은 메모리도 아끼고 exec도 빼는 안처럼 보였지만, 따져 보니 exec보다 센 권한을 core에 주는 안이었습니다. 권한을 확인할 때도 마찬가지로, can-i의 답과 실제 요청의 결과가 달랐습니다. 권한은 실제 요청으로 확인해야 한다는 것을 이번에 배웠습니다.

전체 구조는 [아키텍처 03 - 요청 흐름](/architecture/03-request-flow.html)과 [05 - 권한](/architecture/05-permissions.html)에 정리했습니다.
