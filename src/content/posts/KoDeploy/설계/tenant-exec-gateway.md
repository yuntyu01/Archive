> **요약**
>
> - API 서버(core)가 테넌트 롤의 Pod exec 하나로 웹 터미널, DB 콘솔, 덤프, 복원을 처리해서, core가 탈취되면 모든 테넌트 Pod에서 아무 명령이나 실행할 수 있었습니다.
> - 요청이 올 때 게이트웨이 Pod를 만드는 안은 Pod 생성 권한이 필요했고, 그 권한은 exec보다 셉니다. 그래서 테넌트마다 Go 게이트웨이를 상시로 두었습니다.
> - 브라우저는 32바이트, 30초, 1회용 티켓을 헤더로 내고, core는 테넌트별 HMAC 키로 서명해 부르며, Calico 정책(order 50)이 내부 문을 core Pod에만 엽니다.
> - 11월 13일부터 14일 새벽까지 카나리에서 전체로 넓힌 뒤 core의 `pods/exec`를 회수해 테넌트 롤 권한이 10개에서 8개가 됐고, 11월 23일 기준 게이트웨이 8개가 Pod당 8.8~20.2MiB를 씁니다.

## 들어가는 글

[지난 글](/blog/rbac-rolebinding-vap/)에서 API 서버(core)의 권한을 RoleBinding과 VAP로 테넌트 네임스페이스 안에 가뒀습니다. 그때 테넌트 롤에 마지막까지 남은 것이 Pod exec였습니다. 이 글은 그 exec를 core에서 빼낸 과정입니다.

KoDeploy의 테넌트는 앱마다 하나인 네임스페이스입니다. 사용자의 첫 앱은 `tenant-<hex8>`, 그 뒤 앱은 `app-<hex8>`이라는 이름을 씁니다. 이 글에서 "테넌트별"은 이 네임스페이스마다 하나라는 뜻입니다.

## exec 하나로 하던 일

11월 13일 전까지 core는 사용자가 웹에서 쓰는 기능 네 묶음을 모두 K8s API의 exec로 처리했습니다.

| 기능 | 하던 방식 |
| --- | --- |
| 웹 터미널 (앱, DB, Redis) | tty exec를 WebSocket으로 중계. 바이트를 UTF-8 텍스트로 바꾸고, 창 크기는 본문 안의 접두어로 보냄 |
| DB 콘솔과 표 탐색 | `mysql`, `psql`을 exec하고 stdout, stderr를 나눠 받음 |
| 덤프 | `mysqldump`를 exec하고 stdout을 그대로 내려줌 |
| 복원 | 임시 파일로 `cat`, WebSocket을 닫아 EOF를 대신함, 두 번째 exec, `echo` 마커로 종료 코드 확인 |

권한은 테넌트 롤의 `pods/exec` get과 create였습니다. DB 비밀번호는 core가 Secret에서 읽어 `mysql -p<비밀번호>`처럼 명령에 넣었습니다.

exec는 네임스페이스 안의 어느 Pod에서든 아무 명령이나 실행할 수 있는 권한입니다. core는 외부 요청을 받는 API 서버라서, 탈취되면 모든 테넌트의 DB 셸이 열립니다. 지난 글의 RoleBinding은 이 권한이 닿는 네임스페이스를 테넌트로 좁혔을 뿐, 테넌트 안에서 할 수 있는 일은 줄이지 못했습니다.

## 막으려던 위협

막으려던 위협은 네 가지였고, 바꾼 뒤의 결과는 이렇습니다.

| 위협 | 결과 | 이유 |
| --- | --- | --- |
| core 탈취 | 좁힘 | core는 서명 키를 읽을 수 있어서, 내부 문에 서명한 티켓 발급 요청을 보내 셸을 열 수 있고 SQL, 덤프, 복원도 내부 문으로 직접 부를 수 있습니다. 대상은 테넌트의 앱, DB, Redis 컨테이너로 정해져 있고, 그 밖의 Pod나 명령은 불가 |
| core의 SA 토큰만 유출 | 막음 | K8s API로는 `pods/exec`가 없어 `403`. 토큰으로 HMAC 키 Secret은 읽을 수 있지만, 게이트웨이의 내부 문은 네트워크 정책이 core Pod에서 오는 연결만 받음 |
| 같은 네임스페이스의 사용자 앱이 게이트웨이를 호출 | 막음 | 게이트웨이의 세 포트 모두 직접 접속 거부. 공개 경로로 들어와도 티켓이 필요 |
| 브라우저 쪽 티켓 노출 | 좁힘 | 30초, 1회용, URL 대신 헤더로 전달. 다만 Origin 헤더가 없는 클라이언트(CLI용)는 통과시키므로, 새어 나간 티켓을 30초 안에 먼저 쓰는 것은 못 막음 |

core 탈취를 완전히 막지 못하는 것은 core가 여전히 웹 요청을 받아 사용자 대신 게이트웨이를 부르는 쪽이기 때문입니다. 목표는 core가 할 수 있는 일을 아무 명령에서 정해진 작업 목록으로 줄이는 것이었습니다.

## 다섯 가지 배치

| 안 | 문제 |
| --- | --- |
| ① core에 그대로 | 위의 문제가 그대로 남음 |
| ② 클러스터 공용 게이트웨이 하나 | 게이트웨이 계정에 모든 테넌트의 exec가 필요. 전역 exec가 core에서 게이트웨이로 옮겨갈 뿐 |
| ③ 요청이 올 때 게이트웨이 Pod 생성 | 만드는 쪽(core)에 Pod 생성 권한이 필요 |
| ④ 테넌트마다 만들어 두고 평소 0개, 쓸 때 1개로 | 첫 연결이 늦어짐. 깨우는 쪽에 scale 권한이나 별도 구성 요소가 필요 |
| ⑤ 테넌트마다 1개 상주 | 테넌트 수만큼 메모리 |

③이 이 글 제목의 역설입니다. exec 권한을 빼려고 core에 Pod 생성 권한을 주면, core는 아무 ServiceAccount나 아무 Secret을 마운트한 Pod를 띄울 수 있습니다. 그 Pod 안에서는 마운트한 Secret과 토큰을 그대로 쓸 수 있으니, exec보다 센 권한입니다. 그래서 core와 게이트웨이 모두 Pod 생성 권한을 주지 않는 것을 규칙으로 정했습니다.

②는 권한이 옮겨갈 뿐이고, 나중에 테넌트별로 나누려면 다시 이관해야 해서 처음부터 테넌트별로 가기로 했습니다.

남은 것은 ④와 ⑤입니다. 측정 전에 기준을 먼저 정했습니다.

| 첫 연결이 늘어나는 시간 | 상주 메모리 합계 | 결정 |
| --- | --- | --- |
| 1초 이하 | 워커 할당 가능 메모리의 5% 이상 | ④ 도입 |
| 1초 이하 | 5% 미만 | 보류 |
| 1초 초과 | 상관없음 | 도입하지 않음 |

1초는 Nielsen의 응답 시간 기준에서 생각의 흐름이 끊기지 않는 한계입니다. 11월 13일 운영에 게이트웨이 7개가 떴을 때 상주 RSS 합계는 61MiB로 워커 할당 가능 메모리(17,576MiB)의 0.35%였습니다. 스케줄러가 노드에 잡아 두는 요청으로 봐도 7 × 64Mi = 448Mi로 2.5%였습니다. 어느 쪽으로 봐도 5% 아래라 지연과 상관없이 보류였습니다. ④를 하려면 Argo CD가 replicas를 덮지 않게 `ignoreDifferences`로 빼고, core에 그 Deployment의 scale 권한을 주거나 KEDA 같은 구성 요소를 더해야 합니다. 권한을 줄여 온 방향과 반대이거나 구성 요소가 늘어납니다.

지연은 11월 23일에 시험 앱에서 쟀습니다. 시험 동안 그 앱의 Argo CD selfHeal을 끄고, 게이트웨이를 0개에서 1개로 5번 올리면서 Ready까지와 첫 SQL 실행 성공까지의 시간을 쟀습니다. 끝난 뒤 replicas 1과 selfHeal을 되돌렸습니다.

| 경우 | 범위 | 중앙값 |
| --- | --- | --- |
| 미리 떠 있을 때 SQL 한 번 (5회) | 0.10~0.11초 | 0.10초 |
| 0→1, Ready까지 (4회) | 1.03~2.25초 | 2.14초 |
| 0→1, 첫 SQL 성공까지 (4회) | 1.51~2.78초 | 2.66초 |

Ready가 0.16초였던 2회차는 뺐습니다. 같은 날 다시 재려다 보니 Application에 건 selfHeal 끄기를 ApplicationSet이 몇 초 안에 되돌리고 Argo CD가 replicas를 다시 1로 올렸고, 이 동기화는 sync 기록에 남지 않았습니다. 그 회차는 측정을 시작하기 전에 이미 떠 있던 Pod를 잰 것으로 보입니다. 남은 4회로 보면 첫 연결이 1.4~2.7초 늦어졌고, 4번 모두 1초를 넘었습니다. 이 값에는 무엇이 replicas를 올리는지(core나 KEDA)의 지연이 빠져 있고, 이미지가 이미 있는 노드였습니다. 11월 14일에 이미지를 처음 받는 노드에서는 Ready까지 6초가 걸렸습니다. 기준표로도 ④는 도입하지 않는 쪽이어서 ⑤를 유지했습니다.

## 게이트웨이

`kodeploy-exec`는 Go 1.25와 client-go로 만든 바이너리 하나이고, distroless 이미지에서 UID 65532로 돕니다. 런타임이 있는 앱이면 테넌트 네임스페이스마다 Deployment 하나가 앱 Helm 차트로 그려지고, Argo CD가 앱과 함께 적용합니다.

포트는 셋입니다. 8080은 브라우저가 Envoy를 거쳐 들어오는 공개 문, 8081은 core만 쓰는 내부 문, 9090은 지표와 healthz입니다. 게이트웨이의 ServiceAccount는 자기 네임스페이스의 Pod 목록과 `pods/exec`만 갖고, Secret 권한은 없습니다. 받는 작업도 정해져 있습니다. 공개 문은 앱 셸, DB 콘솔, Redis 콘솔 세 조합만, 내부 문은 티켓 발급(`POST /internal/v1/tickets`)과 SQL 실행, 표 탐색, 덤프, 복원만 받습니다.

## 브라우저 연결과 티켓

웹 터미널의 바이트는 core를 지나지 않습니다. 브라우저가 Cloudflare와 Envoy를 거쳐 게이트웨이 공개 문에 직접 WebSocket을 엽니다. 그 연결에 쓸 티켓은 core가 내부 문(HMAC)으로 요청하면 게이트웨이가 만들어 돌려주고, core가 브라우저에 넘깁니다.

![웹 터미널 연결 순서](/images/posts/tenant-exec-gateway/02.png)

티켓 형식으로는 JWT와 참조 티켓을 비교했습니다.

| | JWT | 참조 티켓 |
| --- | --- | --- |
| 확인 | 받는 쪽이 서명만으로 확인 | 받는 쪽이 저장소에서 조회 |
| 끊기 | 수명 안에서는 못 끊음 | 1회 사용으로 지우거나, 저장소에서 지우면 끝 |
| 크기, 키 | 토큰이 길고, 서명 키를 받는 쪽에 나눠 줘야 함 | 난수만 오감 |

티켓을 만드는 곳과 확인하는 곳이 같은 게이트웨이라서 조회가 메모리 안에서 끝납니다. 그래서 참조 티켓을 골랐습니다. 게이트웨이가 32바이트 난수를 만들어 sha256만 메모리에 두고, 30초 안에 한 번 쓰면 지웁니다. 대기 중인 티켓은 1000개까지입니다. 비대칭 서명이나 Vault도 검토했지만, 막으려는 위협이 core 탈취이고 티켓을 요청하는 쪽이 여전히 core라서 바뀌는 것이 없었습니다.

티켓은 URL에 넣지 않습니다. URL은 서버 접근 로그, Referer, 브라우저 기록에 남습니다. 브라우저는 WebSocket에 `Authorization` 헤더를 붙일 수 없어서 `Sec-WebSocket-Protocol: kodeploy.exec.v1, ticket.<티켓>`으로 보내고, CLI를 위해 `Authorization: Ticket <티켓>`도 받습니다. 게이트웨이는 쿼리 문자열을 아예 보지 않고, 테스트가 이를 고정합니다. 게이트웨이로 가는 HTTPRoute는 `Cookie` 헤더를 지워서 로그인 세션 쿠키가 게이트웨이까지 가지 않습니다.

브라우저에서 오는 요청은 Origin을 허용 목록과 비교합니다. Origin이 없으면 CLI로 보고 통과시킵니다. 이 결정 때문에 위협 표의 마지막 줄이 "좁힘"입니다.

## core에서 게이트웨이까지, HMAC과 네트워크 정책

core는 테넌트 네임스페이스를 만들 때 32바이트 난수 키를 Secret `kodeploy-exec-hmac`에 넣습니다. 게이트웨이는 이 Secret을 읽기 전용 볼륨으로 받아 시작할 때 한 번 읽고, core는 Secret을 읽어 5분 캐시합니다. 테넌트마다 키가 달라서, 한 테넌트의 키가 새도 다른 테넌트의 게이트웨이는 부를 수 없습니다.

서명은 빌더 요청에 쓰던 규칙을 그대로 씁니다. `HMAC-SHA256(키, 시각 + 메서드 + 경로 + 본문)`이고 시각은 ±60초까지 받습니다. 이 규칙은 쿼리 문자열을 서명하지 않습니다. 그래서 내부 문은 쿼리를 읽지 않고, 값은 모두 경로에 넣었습니다. 복원은 `/internal/v1/sessions/restore/{크기}/{sha256}`처럼 기대하는 크기와 해시가 경로에 들어가 서명에 포함됩니다.

내부 문을 core Pod에서만 닿게 하는 것은 Calico NetworkPolicy입니다.

| 방향 | 허용 | 나머지 |
| --- | --- | --- |
| 들어오는 8080 | Envoy 프록시 | |
| 들어오는 8081 | `default` 네임스페이스의 core Pod | |
| 들어오는 9090 | vmagent, 노드(kubelet readiness) | |
| 들어오는 그 밖 | | 같은 네임스페이스의 앱 Pod 포함 모두 거부 |
| 나가는 쪽 | API 서버 6443, DNS | 모두 거부 |

이 정책은 `order: 50`입니다. K8s 기본 NetworkPolicy로는 안 됐습니다. 차트의 테넌트 정책(Calico order 100)이 같은 네임스페이스 전체와 Envoy 네임스페이스를 모든 포트에 허용하고, 사설망을 막는 전역 정책이 order 200에 있습니다. Calico 안에서 K8s NetworkPolicy는 order 1000으로 처리되므로, 그 두 정책이 먼저 결정해 버려 같은 네임스페이스의 앱을 막을 수 없었습니다. 그래서 둘보다 앞선 order 50에서 게이트웨이 Pod만 골라 정했습니다. 11월 13일 같은 네임스페이스의 앱 Pod에서 세 포트 모두 연결 시간 초과가 났고, 대조로 같은 Pod에서 MySQL 3306은 연결됐습니다.

게이트웨이 계정은 자기 네임스페이스의 `pods/exec`를 갖고 있어서, 누군가 이 계정으로 다른 Pod를 띄우면 그 권한을 그대로 씁니다. 그래서 ValidatingAdmissionPolicy로 Pod의 형태를 고정했습니다. 테넌트 네임스페이스에서 이 계정이나 게이트웨이 라벨을 쓰는 Pod는 계정과 라벨이 서로 맞아야 하고, 컨테이너가 정확히 하나이며, init 컨테이너와 ephemeral 컨테이너가 없어야 하고, 이미지가 `ghcr.io/kodeploy/kodeploy-exec@sha256:`으로 고정돼 있어야 합니다.

## 중계

게이트웨이와 브라우저 사이의 채널 번호는 K8s exec(`v5.channel.k8s.io`)와 같게 맞췄습니다. 0 stdin, 1 stdout, 2 stderr, 3 종료 상태, 4 창 크기, 255 닫기입니다. 번호가 같아서 게이트웨이는 바이트를 해석하지 않고 그대로 넘깁니다. 옛 경로처럼 텍스트로 바꾸다 깨진 글자를 대체 문자로 바꾸는 일이 없어졌고, 창 크기도 본문 접두어 대신 채널 4로 갑니다.

API 서버에는 client-go의 WebSocket 실행기(v5)로 먼저 붙고, 업그레이드에 실패하면 SPDY로 넘어갑니다. kubectl과 같은 규칙입니다.

stdout과 stderr는 대화형이 아닌 작업에서 나눠 받습니다. core가 SQL 결과는 stdout에서 표로 읽고, stderr는 오류 메시지로 쓰기 때문입니다. 덤프는 stdout만 gzip 바이트로 흘립니다. 터미널(tty)에서는 K8s가 둘을 합쳐 보냅니다.

세션에는 상한을 뒀습니다. 터미널은 15분 동안 입력이 없으면 닫히고 최대 2시간, 대화형이 아닌 작업은 30분입니다. 동시 세션은 공개 문 3개, 내부 문 4개입니다.

## DB 복원

복원은 두 가지 구조를 비교했습니다. 하나는 exec 한 번으로 업로드를 `mysql`에 바로 흘려 넣는 스트리밍이고, 다른 하나는 Pod 안에 파일로 받은 뒤 확인하고 적재하는 방식입니다. 스트리밍은 단순하지만 받은 바이트가 맞는지 적재 전에 알 수 없고, 중간에 끊기면 DB가 어디까지 바뀌었는지 모릅니다. 파일 방식은 DB를 건드리기 전에 크기와 해시를 확인할 수 있고, 적재 전에 지금 DB를 백업해 되돌릴 지점을 남길 수 있어서 골랐습니다.

![DB 복원 단계](/images/posts/tenant-exec-gateway/03.png)

core는 사용자가 올린 파일의 크기와 sha256을 계산해 경로에 싣고, 256KiB 조각으로 게이트웨이에 보냅니다. 게이트웨이는 단계마다 exec를 하나씩 쓰고, 종료 코드는 K8s exec의 종료 상태로 받습니다.

1. precheck: 남은 백업이 없는지, 필요한 도구가 있는지, 여유 공간이 파일 크기의 두 배 이상인지
2. backup: 지금 DB를 덤프하고, 백업이 공간을 쓴 만큼 업로드 몫이 남았는지 여유 공간을 다시 확인 (MySQL만. PostgreSQL은 load가 한 트랜잭션이라 실패하면 그대로 되돌아가서 이 단계가 없음)
3. upload: Pod 안 파일로 쓰면서 게이트웨이도 바이트 수와 sha256을 계산
4. verify: Pod 안에서 `wc -c`, `sha256sum`, gzip이면 `gzip -t`
5. load: MySQL은 첫 오류에서 멈추고, PostgreSQL은 `ON_ERROR_STOP=1`과 한 트랜잭션으로
6. check: 종료 코드, 표 목록, 행 수
7. rollback: 실패하면 백업으로 되돌림 (MySQL)
8. cleanup: 항상

load 전에 실패하면 결과에 `db_changed: false`가 실리고, core는 5초 간격으로 2번까지 다시 시도합니다. load 중에 연결이 끊기거나 rollback이 실패하면 게이트웨이는 백업을 지우지 않고 남기며, 다음 복원은 precheck에서 거절합니다. 새 복원이 DB를 또 바꾸면 남은 백업과 지금 DB를 비교해 판단할 근거가 사라지기 때문입니다. 복원 파일의 상한은 200MiB입니다.

## 운영 반영과 검증

옛 경로를 지우기 전에 새 경로를 옆에 두고 테넌트 단위로 넓혔습니다. 차트에는 게이트웨이를 그릴 네임스페이스 목록이, core에는 새 경로를 쓸 네임스페이스 목록(`EXEC_AGENT_NAMESPACES`)이 있습니다. 넓힐 때는 차트 먼저(게이트웨이가 뜬 뒤), 그다음 core였고, 좁힐 때는 반대입니다.

| 11/13 오후 | 직접 운영하는 앱 하나(카나리)에서 체크리스트. MySQL 콘솔에서 한글이 깨져 터미널 플래그를 되돌림 |

## 한계

- core는 여전히 서명하고, SQL, 표 탐색, 덤프, 복원에서는 데이터 경로에 있습니다. core가 탈취되면 정해진 작업 안에서는 셸을 열거나 SQL 결과를 볼 수 있습니다.
- 감사 기록은 core와 게이트웨이가 각자 JSON 한 줄씩 stdout에 남기고 티켓 해시로 잇습니다. 둘 다 로그 보존 기간까지만 남고, core가 탈취되면 core 쪽 기록은 믿을 수 없습니다. 게이트웨이 쪽 기록을 따로 보관하는 것이 다음 일입니다.
- 내부 문의 재전송 방지는 ±60초 시각 창뿐이고 nonce가 없습니다. 클러스터 안 평문 HTTP라서, 8081을 core Pod에만 여는 네트워크 정책에 기대고 있습니다.
- 모든 exec 바이트는 여전히 kube-apiserver를 지납니다. 11월 14일 198.5MiB 복원을 master 메모리 3.6GB에서 두 번 시도했는데, API 서버가 버티지 못해 두 번 다 실패했습니다. master를 6GB로 늘린 뒤 같은 크기가 179초에 통과했지만, 적재가 가벼운 주석 덤프였어서 실제 MySQL 적재 메모리는 확인하지 못했습니다.
- 테넌트마다 메모리 요청 64Mi가 상주합니다. 11월 14일 노드 구성(워커 할당 가능 15,576MiB) 기준으로 지금 8개면 512Mi로 3.3%이고, 약 12개면 768Mi로 4.9%가 되어 5%에 닿습니다. 그때 요청을 32Mi로 줄이는 것부터 다시 봅니다.
- 티켓을 헤더로 받게 해서 CLI도 붙을 수 있게 설계했지만, CLI의 exec 명령은 아직 없습니다.
- 지연 측정은 4회(1회 제외), 이미지가 있는 노드에서, kubectl로 직접 replicas를 올린 경우입니다. ApplicationSet이 selfHeal을 되돌리는 것을 막지 않은 채 쟀으므로, 다시 잰다면 ApplicationSet 쪽에서 그 앱을 잠시 빼고 재야 합니다. 첫 SQL 시간에는 측정용 port-forward를 여는 시간이 들어 있습니다.
