> **요약**
>
> - 게임 클라이언트 로그가 초당 수만 건씩 계속 들어오는 상황을 가정하고 수집과 적재 파이프라인을 만들었다.
> - 파일, 큐, DB는 같은 층의 선택지가 아니어서 수집에는 큐(Kafka)를, 적재에는 파일(JSONL)을 썼다.
> - 200을 반환한 로그는 반드시 적재된다는 것을 계약으로 정하고, consumer와 api를 SIGKILL로 종료하는 실험을 포함한 모든 시나리오에서 미적재 0건을 확인했다.
> - `docker compose up -d --build --wait` 한 줄로 뜬다. 첫 기동(빌드 포함)은 19.3초, 부하 중 전체 메모리는 407MB였다.

## 0. 가정한 문제

게임 클라이언트가 보내는 로그(유저 행동, 재화 소비, 시스템 에러)를 받아 쌓는 서버를 만든다고 가정했다.

- 로그는 초당 수만 건이 끊임없이 들어온다.
- 받은 로그는 유실 없이 쌓여야 하고, 유저별로 찾아볼 수 있어야 한다.
- 컨테이너를 재시작해도 쌓인 로그는 남아 있어야 한다.
- 다른 사람 노트북에서도 `docker compose` 명령 한 줄로 떠야 한다.

받는 방법의 후보는 파일에 바로 쓰기, 큐에 넣기, DB에 넣기 세 가지다.

## 1. 구조 선택

### 1-1. 문제 정의와 계약

초당 수만 건이 계속 들어온다는 전제에서 핵심은 소비 속도가 유입 속도를 따라잡는지다. 소비가 조금이라도 느리면 처리하지 못한 양이 매초 쌓이고, 결국 시스템이 버티지 못한다.

유실이 없다는 것은 그대로는 검증하기 어렵다. 네트워크에서 끊긴 요청은 서버가 존재조차 알 수 없기 때문이다. 그래서 책임 범위를 API가 200을 반환한 시점부터로 정하고, 200을 반환한 로그는 반드시 적재된다는 것을 계약으로 삼았다. 검증은 200 응답 수와 적재 건수를 비교하는 방식으로 한다.

단일 노트북에서는 초당 수만 건을 재현할 수 없다. 그래서 낮은 배율에서 구조적 속성(수집과 적재 경로의 분리, 소비가 유입을 따라잡는지)을 실측하고, 실제 규모는 파티션과 컨슈머를 늘리는 확장 방식으로 설명한다.

### 1-2. 세 후보의 층위

|  | 역할 | 층위 |
| --- | --- | --- |
| 큐 | 트래픽을 받아 완충 | 수집 |
| 파일 | 받은 데이터를 보관 | 적재 |
| DB | 받은 데이터를 보관하고 질의 | 적재 |

큐는 데이터의 종착지가 될 수 없다. retention이 지나면 데이터가 사라지므로, 큐를 쓰는 어떤 설계든 적재 단계가 따로 필요하다. 그래서 셋 중 하나를 고르기보다 각 층에 맞는 것을 고르는 방향으로 검토했다.

### 1-3. 수집 층에 큐를 둔 이유

큐 없이 수집하면 API가 적재까지 맡게 되고, 적재 속도가 곧 수집 속도의 상한이 된다.

- DB에 바로 쓰는 경우: 수신이 DB와 동기로 묶여 DB 장애가 그대로 수신 장애가 된다. 처리량도 맞지 않는다. 커밋마다 fsync가 일어나고 커넥션 풀 경합이 생겨서, 초당 수만 건을 요청마다 동기 INSERT로 받기는 어렵다.
- 파일에 바로 쓰는 경우: 부하 때문에 API를 수평 확장하면 로그가 인스턴스마다 다른 파일로 흩어져 수집 문제가 다시 생긴다.

두 방식 모두 규모가 커지면 결국 어딘가에 버퍼가 생긴다. 배치 INSERT는 프로세스 안에 메모리 큐를 두고, fluentd나 vector 같은 도구는 호스트에 에이전트 버퍼를 둔다. 그래서 따져야 할 것은 어차피 필요한 버퍼를 어디에 둘지였다. 유저별 순서, 재처리, 다중 소비는 프로세스마다 따로 있는 버퍼로는 얻을 수 없고 여럿이 함께 읽는 로그가 있어야 가능하므로, 버퍼를 생산자와 장애가 분리된 전용 계층인 브로커로 뺐다.

### 1-4. 브로커 비교와 Kafka 선택

|  | Redis Streams | RabbitMQ | Kafka |
| --- | --- | --- | --- |
| 모델 | 인메모리 로그 | 메시지 브로커 (소비하면 삭제) | 분산 로그 (소비해도 보존) |
| 내구성 | AOF everysec이면 최대 1초 유실 구간 | 영속 큐 | 디스크 로그와 복제 |
| 순서 | 스트림 단위로 직렬 | 경쟁 소비 구조에서 깨짐 | 파티션(key) 단위로 보장 |
| 재처리(replay) | RAM에 남은 것만 | 기본 모델에는 없음 | retention 안에서 오프셋 되감기 |
| 다중 소비 | consumer group | fanout으로 물리 복제 | consumer group (각자 진행) |
| 확장 방법 | 단일 스레드가 병목 | 큐가 쌓이면 성능 저하 | 파티션 수를 설계에서 정함 |

- Redis Streams를 뺀 이유: 셋 중 Kafka와 가장 비슷하다(append 로그와 consumer group을 차용했다). 하지만 Kafka는 디스크가 본체이고 메모리가 가속 역할인 반면, Redis는 메모리가 본체이고 디스크(AOF)가 백업이다. 그래서 문제가 세 가지 있다. retention이 RAM 용량에 묶여 재처리할 수 있는 범위가 좁다(초당 수만 건에 건당 수백 바이트면 시간당 수십 GB다). AOF everysec 설정에서는 최대 1초의 유실 구간이 남고, 이를 없애면 지연이 크게 늘어난다. 스트림 하나가 단일 스레드라서 키 기준 분산을 애플리케이션에서 직접 샤딩해 구현해야 한다. 트래픽이 초당 수백에서 수천 건이고 이미 Redis를 운영 중이라면 좋은 후보지만, 이번 전제는 그 규모를 넘는다.
- RabbitMQ를 뺀 이유: 기본 모델에서 메시지는 소비되면 삭제된다. 파이프라인 버그를 고친 뒤 다시 처리할 수 없고, 여러 소비자가 경쟁하는 구조에서는 순서가 보장되지 않는다. RabbitMQ가 잘하는 일은 작업 분배와 라우팅이다.
- Kafka를 고른 이유: 로그 수집에 필요한 네 가지인 유저별 순서(partition key), 재처리(retention과 offset reset), 다중 소비(적재와 분석이 각자의 속도로 읽음), 순서를 유지하며 처리량을 늘리는 방법(파티션)을 별도 기능 없이 기본 모델로 모두 충족한다.
- 표에 없는 Kafka 호환 구현체들도 모델은 같아서, 차이는 자원 사용량과 지연 정도다. 이 차이는 환경과 버전에 따라 달라 이론만으로 판단하기 어려워서, 생태계와 운영 자료, 관리형 서비스 선택지가 가장 많은 Kafka를 기본으로 했다.

### 1-5. 적재 층에 파일을 둔 이유

원본 로그는 append-only이고 수정이나 삭제가 없다(이미 일어난 이벤트는 나중에 바뀌지 않는다). 적재 층에 필요한 것은 네 가지다.

| 요구 | 근거 |
| --- | --- |
| 내구성 있는 순차 쓰기 | 유실 없이 적재해야 하고, 재시작해도 보존돼야 한다 |
| 저비용 무한 누적 | 초당 수만 건이 계속 쌓인다 |
| 스키마 수용 | 유저 행동, 재화 소비, 시스템 에러가 함께 들어온다 |
| 후속 분석 접근 | 요구사항에 적혀 있지는 않지만 로그를 쌓는 이유다 |

- DB(RDB와 NoSQL 모두)를 뺀 이유: 비용은 세 가지가 드는데 얻는 것이 없다. DB의 강점인 인덱스 조회와 부분 갱신이 위 요구에 없기 때문이다. RDB는 게임마다 다른 이벤트 필드 때문에 스키마 관리 부담도 생긴다.
    - 쓰기 증폭: 1건이 저널, 테이블, 인덱스에 나뉘어 여러 번 쓰인다(문서형 DB의 `_id` 인덱스는 끌 수도 없다). 파일 append는 순차 쓰기 한 번으로 끝난다.
    - 상시 운영비: 읽지 않는 시간에도 컴퓨트가 켜져 있어야 하고, 계속 쌓이는 데이터에 비례해 샤딩과 백업 부담이 커진다.
    - 추출 단계: 분석 도구(Athena, Spark)는 파일을 직접 스캔하므로 결국 파일로 내보내는 단계가 필요하다.
- 파일(JSONL)을 고른 이유: 스키마가 달라도 그대로 받을 수 있고, 용량 대비 비용이 가장 낮으며, 분석 도구가 직접 읽을 수 있다. 도커 볼륨에 두면 컨테이너를 재시작해도 남는다.

### 1-6. 최종 구조

- 수집: 큐가 트래픽을 받고, 적재 쪽 장애가 API로 번지지 않게 막는다.
- 적재: 파일과 볼륨이 append-only 데이터를 적은 비용으로 보관한다.
- 조회: 적재 경로는 유저를 구분하지 않는다. 유저별 조회는 적재된 파일을 필터링하는 방식이고, 프로덕션에서는 Athena 같은 도구가 맡는다.

### 1-7. 설계 결정

#### API

| 결정 | 근거 |
| --- | --- |
| ack 후 200 응답 (`send_and_wait`, `acks=all`, idempotence) | 전송 확인 없이 응답하면 API가 죽는 순간 200은 나갔지만 브로커에 도달하지 않은 로그가 생긴다(V-4′에서 확인). 처리량은 `linger.ms=5` 배칭으로 유지했다(p99 33.9ms). `acks=all`은 RF=1에서는 효과가 없지만, RF=3으로 바꾸면 코드 수정 없이 적용된다 |
| `key=user_id` | 파티션 안에서 유저별 순서를 보장한다. 전역 순서는 요구사항이 아니다 |
| SIGTERM 시 flush | 정상 종료 때 producer 버퍼에 남은 로그가 유실되지 않게 한다 |

#### Kafka

| 결정 | 근거 |
| --- | --- |
| 파티션 3 | 병렬 처리 한도를 미리 확보한다. 운영을 시작한 뒤 파티션을 늘리면 key 매핑이 바뀌어 유저별 순서가 끊긴다 |
| 토픽 명시 생성 (kafka-init) | 운영에서는 토픽 자동 생성을 끄는 것이 일반적이다. 파티션 수가 전역 기본값 대신 토픽 정의를 따른다 |
| JVM 힙 512MB 고정 | 다른 사람 노트북에서도 떠야 하므로 상한을 정했다. 부하 중 전체 실사용량은 407MB였다 |

#### Consumer

| 결정 | 근거 |
| --- | --- |
| flush, fsync, 커밋 순서 (at-least-once) | 커밋하기 전에 디스크 기록을 확정한다. flush 전에 커밋하면 커밋은 됐지만 파일에는 없는 로그가 생기고, flush만 하고 커밋하면 데이터가 커널 캐시에 남아 전원이 끊길 때 최대 30초 분량이 같은 상태가 된다. 대신 최대 1배치가 중복될 수 있는데, 중복은 나중에 제거할 수 있지만 유실은 복구할 수 없다 (V-4, V-5 A/B) |
| 소스 좌표 `_src:{파티션,오프셋}` 기록 | 브로커가 부여한 변하지 않는 고유 좌표를 각 줄에 붙여, consumer 재처리로 생긴 중복을 구별할 수 있게 한다 |
| JSONL 그대로 적재 (ELT) | flush 경계를 하나로 유지하고, 쓰는 경로에서 분류 로직을 뺀다. 분류는 읽을 때 한다 |
| 시간 파티셔닝과 part 파일 | `dt=/hour=` 단위로 나눠 파일이 끝없이 커지지 않고, 시간 범위 단위로 읽거나 지울 수 있다. 파일을 컨슈머별로 따로 두어 `--scale` 때 동시 append 충돌이 없고, 파일 교체는 배치 경계에서만 해서 flush, fsync, 커밋 순서가 깨지지 않는다 |

#### 환경 (compose)

| 결정 | 근거 |
| --- | --- |
| api healthcheck (소켓 probe) | `--wait`가 api가 요청을 받을 준비가 될 때까지 기다리게 해서 기동 직후 수신 실패를 막는다. 검증 중 원인을 찾아 추가했다(실패 92건에서 0건으로) |
| 네트워크 분리 (frontend/backend) | 외부에 여는 지점을 api 하나로 제한해, 인증 없는 브로커와 적재 데이터가 호스트에 노출되지 않게 한다 |
| `container_name` 미지정 | 이름을 고정하면 복제본이 같은 이름을 요구해 충돌한다. compose가 이름을 붙이게 두어야 `--scale consumer=N`으로 늘릴 수 있다 |

### 1-8. 비용과 운영 부담

- 로컬 자원: 다른 사람 노트북에서도 떠야 하므로 자원 사용량도 요구사항에 포함된다. Kafka 힙을 512MB로 제한했고, 부하 중 전체 스택은 407MB를 썼다(V-6).
- 운영 부담: Kafka는 후보 중 운영 부담이 가장 크다(파티션 재배치, 리밸런싱, 그룹 모니터링). 이 부담은 받아들이되 줄이는 방향으로 대응했다.
- 알람은 consumer lag 하나에만 건다: lag은 생산과 소비 속도 차이가 쌓인 값이라, 컨슈머 종료, I/O 지연, 재시도 반복, 용량 부족처럼 소비 쪽에서 생기는 문제는 결국 이 숫자에 드러난다. CPU, 메모리, I/O 같은 원인 지표는 수집만 하고 알람은 증상에만 건다. 원인 지표에 알람을 걸면 오탐과 미탐이 모두 생기기 때문이다. 판단은 값의 크기보다 증가 추세로 하고, 계속 늘어나면 `--scale consumer=N`으로 대응한다.

### 1-9. 한계와 프로덕션 전환

- 브로커 단일 장애점: 브로커 1대, RF=1이다. 데이터 디렉터리를 볼륨에 마운트해서 재시작하면 복구되지만, 프로덕션에서는 브로커 3대, RF=3, `min.insync.replicas=2`, `acks=all`로 1대 장애까지 중단과 유실 없이 버티게 한다. API와 consumer는 stateless라 수평 확장으로 대응한다.
- at-least-once의 중복: 좌표로 구별할 수 있는 것은 consumer 재처리로 생긴 중복까지다. 클라이언트가 재전송한 로그는 새로 produce되어 새 좌표를 받기 때문에 구별되지 않는다. 이를 막으려면 클라이언트가 붙인 이벤트 uuid가 필요하다(서버 범위 밖).
- 로컬 내구성의 한계: flush, fsync, 볼륨은 각각 프로세스 크래시, 전원 차단, 컨테이너 재생성에 대비하지만, 디스크 자체가 사라지면 로컬 파일은 복구할 수 없다. 이 경우는 브로커 retention 안에서 offset을 되감아 복구하고(지금은 CLI로 수동), 프로덕션에서는 적재 대상이 S3로 바뀌어 이 문제 자체가 없어진다.
- 보존 정책 없음: 시간 파티셔닝으로 파일은 나뉘지만, 오래된 파티션을 지우거나 옮기는 기능은 구현하지 않았다. 데모 규모(수 MB, 단기 실행)에서는 디스크 부담이 없어 범위에서 뺐다. 프로덕션에서는 S3 수명주기 정책이 이 역할을 맡는다.

## 2. 띄우고 관측하기

요구사항은 Docker와 Docker Compose v2(`--wait` 플래그 사용)뿐이고, 다른 도구는 필요 없다.

```bash
docker compose up -d --build --wait
```

`--wait`는 모든 서비스가 healthy가 될 때까지(api는 요청을 받을 준비가 될 때까지) 기다리므로, 명령이 끝나면 바로 요청을 보낼 수 있다.

로그 전송과 적재 확인 예시는 3절 V-2에 있다.

부하 재현(외부 도구 없이):

```bash
python3 scripts/send_seq.py --n 60000 --concurrency 50
```

lag 관측:

```bash
watch -n1 'docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --group log-sink --describe'
```

- 컨슈머 증설: `docker compose up -d --scale consumer=3`
- 초기화: `docker compose down -v`
- 환경 변수 `ROTATE_INTERVAL`: part 파일 교체 주기 (데모 60s, 운영 3600s 권장)
- 환경 변수 `FSYNC`: 커밋 전 `fsync()` 수행 여부 (기본 true)

## 3. 검증 결과

브로커 간 차이(AOF 유실 구간, 소비 시 삭제, retention 보존)는 각 시스템 문서에 나온 설계 사항이라 로컬에서 재현하지 않았다. 실험은 채택한 구조가 1-1의 계약을 지키는지만 확인하고, 예측이 틀린 경우도 그대로 기록했다. 아래 수치는 모두 같은 구성, 같은 세션에서 측정했다.

V-1(기동)은 2절의 `--wait` 통과로 판정되므로 따로 절을 두지 않았다.

### V-3. 지속 유입 처리

| 지표 | 값 |
| --- | --- |
| 부하 중 lag (10s/30s/종료) | 50 → 0 → 0. 계속 늘지 않아 소비가 유입을 따라잡고 있다 |
| 부하 A (send_seq, 60,000건 고정) | 41.0초 소요, 약 1,463 rps, 전건 200, 적재 60,000건 (미적재 0, 중복 0) |
| 부하 B (hey, 60초 고정, 단일 키) | 2,596 rps, p50 18.1ms, p99 33.9ms, max 63.2ms, 155,821건 전건 200 |
| 부하 종료 후 잔여 lag | 0. 종료 시점에 이미 다 처리했다 |
| 파일 교체 | `ROTATE_INTERVAL=60`, 41초 부하 중 경계를 한 번 지나 part 파일 2개로 나뉜 것을 확인 |

두 부하는 키 분포가 다르다. hey는 단일 키(파티션 1개)를 쓰고 send_seq는 키 100개(파티션 3개에 분산)를 쓴다. 그런데 파티션 하나만 쓴 hey가 더 빨랐다(2,596 rps와 1,463 rps). 컨슈머가 1개면 파티션이 몇 개든 병렬 처리 이득이 없어서, 이 구간에서는 파티션 수가 성능 한도를 정하지 않는다.

차이는 부하 생성기에서 나왔다. send_seq는 파이썬 스레드로 동작해서 부하 중 클라이언트 프로세스가 CPU 101%로 한 코어를 다 쓴다. 따라서 1,463 rps는 부하 생성 스크립트가 낼 수 있는 한도였고, 파이프라인 쪽 한도는 api가 정한다(V-6). 절대값은 세션마다 달라지므로 같은 세션 값끼리만 비교했다.

### V-4. consumer SIGKILL

전송 중 consumer를 SIGKILL로 종료하고 다시 띄운 뒤, 200 목록과 적재 목록을 대조했다(`scripts/v4.sh consumer`).

| 항목 | 값 |
| --- | --- |
| 200 응답 | 10,000 / 10,000 (클린 기동 직후 전건 200) |
| 200을 받았지만 적재되지 않은 건 | 0 |
| 중복 (총 10,050 − 고유 10,000) | 50. 커밋 전 배치가 다시 전달된 것으로, `_src` 좌표가 같아 구별된다 |

커밋 전에 처리된 만큼 중복이 날 것으로 예측했지만, 종료 시점을 바꿔 가며 한 처음 세 번은 중복이 0건이었다. 중복은 `flush()`가 끝나고 `commit()` 전인 짧은 구간에 종료돼야 생기는데, 배치 주기가 짧아서(500건 이하, 1초 미만) SIGKILL이 그 구간을 자주 비켜 갔다. at-least-once는 최소 1회 전달을 뜻하므로 중복 0건도 정상 동작이다. 네 번째 시도(t=3.1s)에서 그 구간에 걸려 중복 50건이 나왔다.

중복된 로그의 분포도 이 설명과 맞는다. 50건은 세 파티션에 12건, 16건, 22건으로 나뉘었고, 파티션 안에서 오프셋이 연속이었다(p0은 1163~1174). 커밋되지 못한 마지막 배치가 통째로 다시 전달된 것이다. 중복된 줄은 `_src`까지 똑같다.

```
{"user_id": "user_43", "seq": 4143, ..., "_src": {"p": 0, "o": 1163}}
{"user_id": "user_43", "seq": 4143, ..., "_src": {"p": 0, "o": 1163}}
```

적재된 전체를 `_src` 기준으로 중복 제거해 봤다.

```bash
docker compose exec consumer sh -c "find /data/logs -name '*.jsonl' | xargs cat" \
  | python3 -c "import sys,json; print(len({(r['_src']['p'],r['_src']['o']) for r in map(json.loads,sys.stdin)}))"
```

```
10000
```

10,050줄이 10,000건으로 줄었고, 200 응답 수와 정확히 같다. 중복은 걸러낼 수 있고 유실은 없다는 설계 의도대로 동작했다.

### V-4′. api SIGKILL

같은 절차에서 종료 대상만 api로 바꿨다(`scripts/v4.sh api`).

| 항목 | 값 |
| --- | --- |
| 200 응답 | 8,353 |
| 200을 받았지만 적재되지 않은 건 | 0 |
| 적재된 고유 건수 | 8,379 (+26) |

미적재가 0건인 이유는 응답 순서에 있다. `send_and_wait`로 브로커 ack를 받은 뒤에만 200을 반환하므로, 200이 나갔다면 이미 브로커에 기록된 것이다. 전송 확인 없이 응답하는 구현이었다면 버퍼에만 있던 메시지에도 200이 나가서 여기서 미적재가 생겼을 것이다.

26건이 더 많은 것은 반대 방향의 차이다. ack까지 끝났지만 HTTP 응답 직전에 SIGKILL이 들어와서, 적재는 됐는데 클라이언트는 실패로 기록한 경우다. 계약은 한 방향으로만 성립한다. 200을 받으면 적재가 보장되지만, 실패 응답을 받았다고 적재되지 않은 것은 아니다. ack와 응답 사이의 구간은 없앨 수 없어서, 오류가 어느 쪽으로 나게 할지만 정할 수 있다.

### V-5. 장애 격리

부하 중(t=8s)에 consumer를 멈췄다. API는 에러 없이 30,000건 모두 200을 반환했고, 처리하지 못한 양이 lag 11,351까지 쌓였다. consumer를 다시 띄우자 13초 만에 모두 처리됐다(`scripts/v5.sh`).

13초 중 대부분은 처리 시간이 아니다. 같은 실험을 초 단위로 계측하며 다시 돌리면(피크 10,743) 재기동 후 8.1초까지는 lag이 피크 값 그대로이고, 9.7초에 0이 된다. 앞의 8초는 컨테이너 기동과 그룹 재참여 시간이고, 실제 처리는 1.6초 이내로 초당 6,700건 이상이다. `v5.sh`가 보여 주는 13초는 여기에 1초 폴링과 0을 두 번 연속 확인하는 조건이 더해진 상한값이다. V-3에서는 부하 생성 스크립트가 병목이라 컨슈머가 초당 1,463건을 따라간다는 것만 확인했는데, 밀린 양을 한꺼번에 처리하는 이 실험에서 더 높은 처리 능력이 확인됐다.

적재가 멈춰도 수신은 계속됐다. API가 DB에 바로 쓰는 구조였다면 같은 상황에서 수신 자체가 실패했을 것이다. 큐를 도입한 가장 큰 이유를 이 실험으로 확인했다.

같은 실험을 `FSYNC=false`로 다시 돌리면 전건 200, 피크 12,670, 처리 11초다. fsync를 켠 쪽이 13초였지만 피크는 오히려 낮았고(11,351), 두 값의 차이는 `v5.sh`의 폴링 한 번(약 2.6초) 안에 들어간다. 이 해상도로는 fsync 비용을 따로 측정할 수 없었다. 배치당 fsync 한 번을 최대 500건이 나눠 부담한다는 설계 근거는 그대로지만, 그 크기를 이 실험으로 재지는 못했다.

### V-6. 자원 사용량

| 컨테이너 | 유휴 | 부하 중 | CPU (부하) |
| --- | --- | --- | --- |
| kafka | 275 MB | 354 MB | 69% |
| api | 34 MB | 36 MB | 110% |
| consumer | 17 MB | 17 MB | 8% |
| 합계 | 326 MB | 407 MB |  |

CPU%는 코어 1개를 100%로 센다. 그래서 각 컨테이너가 자기 한도에 얼마나 가까운지로 봐야 한다. kafka는 JVM 다중 스레드라 여러 코어를 쓸 수 있어서 69%면 여유가 크다. api는 uvicorn 단일 워커, 즉 파이썬 프로세스 하나라서 GIL 때문에 한도가 약 100%인데, 이미 110%로 한도에 붙어 있다. 이 세션에서 약 2,600 rps가 상한이 된 이유다. consumer는 8%로 여유가 많다.

병목은 api다. api는 stateless라 워커나 레플리카를 늘리면 해결되고, 설계를 바꿔야 하는 문제는 아니다.

### 기동 직후 수신 실패 92건

계약 검증(V-4)을 돌리다 200 응답이 9,908/10,000으로 나와 원인을 추적했다. consumer 종료와는 관계없는, 기동 직후 수신 준비 문제였다.

처음에는 첫 produce에서 토픽이 자동 생성되느라 늦어지는 것으로 추정했다. 하지만 kafka-init으로 토픽을 미리 만든 뒤에도 115건(seq 0~114, 연속)이 실패해서 이 가설은 버렸다.

실제 원인은 api에 healthcheck가 없는 것이었다. `--wait`는 컨테이너가 running 상태가 될 때까지만 기다리는데, uvicorn은 lifespan(producer 시작)이 끝난 뒤에야 포트를 연다. 그 사이에 도커 프록시가 연결을 받았다가 reset했다. 소켓 probe healthcheck를 추가해서 `--wait`가 api의 리슨 준비까지 기다리게 하자, 클린 기동 직후 10,000건이 모두 200을 받았다(92건에서 0건).

readiness는 프로세스가 떴는지보다 요청을 받을 수 있는지로 판정해야 한다. `--wait`의 기본 기준(running)은 앞의 것이라서, 뒤의 것을 확인하는 healthcheck를 따로 정의해야 한다. 1-7의 api healthcheck 결정이 여기서 나왔다.

## 4. AWS로 옮긴다면

ALB(public, 2AZ)에서 ECS Fargate(private, 2AZ), Kinesis Data Streams, Firehose를 거쳐 S3에 쌓는 구성이다.

![AWS 아키텍처](/images/posts/ingame-log-pipeline/02.png)

로컬 compose 구조를 관리형 서비스로 그대로 옮긴 형태다.

| 로컬 (compose) | AWS |
| --- | --- |
| Kafka (파티션) | Kinesis Data Streams (샤드) |
| Consumer와 도커 볼륨의 JSONL | Firehose, S3 |
| `dt=/hour=/part-*` 레이아웃 | Firehose S3 파티셔닝 (경로 형태 동일) |
| backend 네트워크 (비노출) | private subnet |
| api healthcheck | ALB 타깃 헬스체크 |

- 관리형 서비스를 쓰는 이유: 1-8에서 말한 Kafka 운영 부담(파티션 재배치, 리밸런싱, 그룹 모니터링)을 AWS에 맡기면서 샤드 기반 확장 방식은 유지한다. 운영 부담을 비용으로 바꾸는 결정이고, 관리형 요금은 자체 운영에 드는 실제 비용(인력 시간, 온콜, 장애 위험)과 비교해야 한다.
- 비용 설계: S3 수명주기 정책(Standard에서 Glacier로), Firehose 단계의 Parquet 변환(저장과 스캔 비용 절감), 수집 경로의 VPC 엔드포인트(NAT 데이터 처리 비용 회피).
- Terraform 범위: 수집부터 적재까지 전체 경로를 작성했다. VPC, Subnet, IGW, NAT, ALB, ECS Fargate(이미지는 자리표시), Kinesis(샤드 3, 로컬 파티션 3에 대응), Firehose(`dt=/hour=` prefix, 60초 버퍼로 ROTATE_INTERVAL에 대응), S3(90일 뒤 Glacier, 5년 뒤 삭제)다. 위 대응표의 구조가 코드에서도 그대로 성립하고, `terraform validate`를 통과했다(실제 프로비저닝은 하지 않았다).
